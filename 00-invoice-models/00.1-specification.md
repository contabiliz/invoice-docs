# 00.1 invoice-models

## 00.1.1 Overview

`invoice-models` is the shared type library for the entire backend. It is imported by every other package (`invoice-api`, `invoice-pipeline`, `invoice-processors`) and defines the contracts between them. It has no infrastructure dependencies and no business logic beyond field validation and normalization.

The package exports two things:

1. **Pydantic models** — typed, validated data structures used as request/response schemas, task payloads, and extraction results.
2. **Validator functions** — standalone, importable functions that implement the validation and normalization logic for fiscal data types. These are used both inside the Pydantic models and by `invoice-processors` during candidate scoring.

---

## 00.1.2 Architecture Decision Records

### ADR-001 — Validators as Standalone Functions, Not Only Pydantic Validators

**Decision:** Validation logic for fiscal data types (CNPJ, CPF, moeda_brl, data, etc.) is implemented as standalone functions in `invoice_models.validators`, not exclusively as Pydantic `@field_validator` decorators. The Pydantic models call these functions internally.

**Reasons:**
- `invoice-processors` needs to validate extraction candidates **during scoring**, before constructing any Pydantic model. A candidate CNPJ that fails the check-digit algorithm receives `type_score = 0.0` and is discarded. This happens mid-pipeline, not at model construction time.
- If validation logic lived only inside Pydantic validators, the processor would have to duplicate it or construct and catch `ValidationError` in a hot loop — both are wrong.
- Standalone functions are the single source of truth. The Pydantic models call them; the processor calls them; the logic exists once.

**Consequences:** `invoice_models.validators` is a public API. Breaking changes (renaming a function, changing its return type) require coordinated updates in `invoice-processors` and any other caller.

---

### ADR-002 — Separate Result Types Per Branch

**Decision:** Each processor branch has its own result type (`NfeXmlResult`, `PdfExtractionResult`, `ImageExtractionResult`). There is no single `ExtractionResult` union type.

**Reasons:**
- XML, PDF, and image documents yield structurally different data. XML always has a well-defined `items` list with NCM and CFOP per line. Image extraction may yield partial fields with confidence scores. Forcing them into a shared union adds nullable fields and conditional logic everywhere.
- The database stores `extracted_data` as JSONB — it tolerates different shapes per `doc_type`. The `doc_type` column already tells consumers which shape to expect.
- A common base class (`FiscalExtractionResult`) can hold fields that truly exist on all three (e.g., `cnpj_emitente`, `valor_total_nota`), but the subtypes are not interchangeable.

**Consequences:** Workers construct the correct subtype based on `doc_type`. The `extracted_data` column always matches the shape defined by the subtype for that `doc_type`.

---

### ADR-003 — Task Payloads Are Models, Not Dicts

**Decision:** Celery task payloads are defined as Pydantic models in `invoice_models.tasks`. Workers receive typed payloads, not raw dicts.

**Reasons:**
- Task payloads cross the boundary between the Consumer (which publishes) and the workers (which consume). Without a shared type, field renames or additions require finding all call sites manually.
- Pydantic models validate the payload at deserialization time. A malformed task payload fails immediately with a clear error, not silently with a `KeyError` mid-task.
- `invoice-models` is the one place where this contract is defined. The Consumer imports the model to construct the payload; the worker imports the same model to receive it.

**Consequences:** Celery tasks are called with `.model_dump()` and received via `Model.model_validate(payload)`. The payload schema is versioned — breaking changes require a migration strategy (parallel fields, version field) before old tasks in the queue are consumed.

---

### ADR-004 — No Infrastructure Dependencies

**Decision:** `invoice-models` must not import `celery`, `asyncpg`, `redis`, `httpx`, `boto3`, `supabase`, or any I/O library.

**Reasons:**
- The package is imported by all others. Any infrastructure dependency it introduces is transitively imported everywhere, bloating container images and creating unexpected coupling.
- Pure Python + Pydantic ensures the package can be imported in any environment, including CI test runners without infrastructure credentials.

**Consequences:** If a model needs a computed field that requires I/O (e.g., looking up a value in the database), that logic does not belong in the model. It belongs in the layer that has database access.

## 00.1.4 Validator Functions (`invoice_models.validators`)

All validators return a `ValidationResult`:

```python
@dataclass(frozen=True)
class ValidationResult:
    ok: bool
    normalized_value: str | None  # None if ok is False
    reason: str | None            # None if ok is True
```

| Function | Input | Validates | Normalizes to |
|---|---|---|---|
| `validate_cnpj(raw: str)` | Any string | 14-digit check digit algorithm | `XX.XXX.XXX/XXXX-XX` |
| `validate_cpf(raw: str)` | Any string | 11-digit check digit algorithm | 11-digit string (no formatting) |
| `validate_cpf_ou_cnpj(raw: str)` | Any string | Delegates by digit count | Same as above |
| `validate_moeda_brl(raw: str)` | Any string | Brazilian decimal format | Decimal-compatible string (e.g. `"1234.56"`) |
| `validate_data(raw: str)` | Any string | DD/MM/YYYY, YYYY-MM-DD, DD-MM-YYYY, DD/MM/YY | `YYYY-MM-DD` |
| `validate_texto_numerico_44(raw: str)` | Any string | Exactly 44 digits | 44-digit string |
| `validate_cidade_uf(raw: str)` | Any string | City name + valid 2-letter UF code | `CIDADE/UF` |
| `validate_texto(raw: str)` | Any string | Non-empty after whitespace collapse | Whitespace-normalized string |

**Usage in `invoice-processors`:**

```python
from invoice_models.validators import validate_cnpj

result = validate_cnpj(raw_text)
type_score = 1.0 if result.ok else 0.0
normalized = result.normalized_value  # used in the final FieldOutput
```

**Usage in Pydantic models:**

```python
from invoice_models.validators import validate_cnpj

class NfeXmlResult(BaseModel):
    cnpj_emitente: str

    @field_validator("cnpj_emitente", mode="before")
    @classmethod
    def _cnpj(cls, v: str) -> str:
        result = validate_cnpj(v)
        if not result.ok:
            raise ValueError(result.reason)
        return result.normalized_value
```

## 00.1.5 Task Payload Models (`invoice_models.tasks`)

Published by the Consumer, consumed by workers.

```python
class BaseTaskPayload(BaseModel):
    document_id: UUID
    batch_id: UUID
    user_id: UUID
    s3_key: str

class XmlTaskPayload(BaseTaskPayload):
    doc_type: Literal["xml"] = "xml"

class PdfTaskPayload(BaseTaskPayload):
    doc_type: Literal["pdf"] = "pdf"

class ImageTaskPayload(BaseTaskPayload):
    doc_type: Literal["img"] = "img"
    source: Literal["direct", "pdf_fallback"] = "direct"
    # source="pdf_fallback" when rerouted from the PDF branch
```

`source` on `ImageTaskPayload` is used by `invoice-pipeline` to avoid re-running PDF processing if the image task fails and retries.

## 00.1.6 Extraction Result Models (`invoice_models.extraction`)

### Common

```python
class FieldOutput(BaseModel):
    value: str | None
    confidence: float          # 0.0–1.0, from scoring pipeline (PDF/image only)
    method: str                # "xpath", "ngram", "alias", "gemini"
    raw_text: str | None       # Original text before normalization
    errors: list[str]          # Validation/extraction error reasons
```

### XML Result

```python
class NfeLineItem(BaseModel):
    numero_item: int
    codigo_produto: str
    descricao: str
    quantidade: Decimal
    unidade: str
    valor_unitario: Decimal
    valor_total_item: Decimal
    ncm: str
    cfop: str

class NfeXmlResult(BaseModel):
    chave_acesso: str
    cnpj_emitente: str          # validated + normalized by validate_cnpj
    nome_emitente: str
    documento_destinatario: str # CNPJ or CPF
    nome_destinatario: str
    data_emissao: date
    valor_total_nota: Decimal
    numero_nota: str
    serie: str
    items: list[NfeLineItem]
```

### PDF Result

```python
class PdfLineItem(BaseModel):
    # Canonical column names, normalized from raw PDF header text
    descricao: str
    quantidade: Decimal | None
    unidade: str | None
    valor_unitario: Decimal | None
    valor_total_item: Decimal | None
    cfop: str | None
    ncm: str | None

class PdfExtractionResult(BaseModel):
    chave_acesso: FieldOutput
    cnpj_emitente: FieldOutput
    nome_emitente: FieldOutput
    documento_destinatario: FieldOutput
    nome_destinatario: FieldOutput
    data_emissao: FieldOutput
    valor_total_nota: FieldOutput
    numero_nota: FieldOutput
    serie: FieldOutput
    items: list[PdfLineItem]
    table_confidence: float     # composite score from best table strategy
```

PDF fields are wrapped in `FieldOutput` (not bare values) because the scoring pipeline produces per-field confidence and method metadata. This is useful for debugging extraction quality and for identifying which fields need improvement.

### Image Result

```python
class ImageExtractionResult(BaseModel):
    cnpj_emitente: str | None
    nome_emitente: str | None
    documento_destinatario: str | None
    nome_destinatario: str | None
    data_emissao: date | None
    valor_total_nota: Decimal | None
    numero_nota: str | None
    items: list[ImageLineItem]
```

Image fields are bare values (not `FieldOutput`) because Gemini does not produce per-field confidence scores. All fields are nullable — image extraction is best-effort.

### Routing Signal

```python
class RoutingOverride(str, Enum):
    IMAGE = "image"

class ProcessorResult(BaseModel):
    """Wrapper returned by all processor branches to invoice-pipeline."""
    result: NfeXmlResult | PdfExtractionResult | ImageExtractionResult | None
    is_terminal_failure: bool = False
    terminal_reason: str | None = None
    routing_override: RoutingOverride | None = None
    # routing_override="image" → PDF worker reroutes to image branch
```

`invoice-pipeline` checks `ProcessorResult` fields in order:
1. `is_terminal_failure` → mark document `failed`, no retry
2. `routing_override == "image"` → publish `ImageTaskPayload`, return without DB write
3. Otherwise → write `result` to `documents.extracted_data`

## 00.1.8 What Not To Do

**Do not put infrastructure code in this package.**
No database queries, no Redis calls, no HTTP clients. If a model needs a value that requires I/O to compute, that belongs in the caller.

**Do not add utils, helpers, or constants that are not type definitions.**
`invoice-models` is not a shared utilities library. If something is not a Pydantic model, a validator function, or a type alias, it does not belong here.

**Do not implement validation logic in both a standalone function and a Pydantic validator separately.**
The Pydantic validator must call the standalone function. Two independent implementations of CNPJ validation will eventually diverge.

**Do not make `NfeXmlResult`, `PdfExtractionResult`, and `ImageExtractionResult` interchangeable.**
They are not a union that can be substituted. Workers select the correct type based on `doc_type`. Code that needs to handle all three should use `ProcessorResult.result` with a type check, not try to cast between subtypes.

**Do not add fields to task payloads without a migration plan.**
Tasks may be in the Redis queue when a new worker version is deployed. Adding a required field to `XmlTaskPayload` will cause the new worker to reject tasks published by the old Consumer. Use `Optional` fields with defaults for additive changes; coordinate deployments for breaking changes.

**Do not expose internal processor types through this package.**
`WordBox`, `Edge`, `Vertex`, `ScoredCandidate`, `KeyCandidate` are internal to `invoice-processors`. They must not be imported by or defined in `invoice-models`.
