# 02.2 API Performance Reference

Concrete call counts, external service interactions, polling cost, and latency targets for the full API surface. Use this as a cost model when planning capacity, evaluating client design, or estimating external service usage.

---

## 02.2.1 API Calls per Batch (Happy Path)

Every batch that enters the system and completes successfully produces exactly **3 client-initiated API calls** plus a variable number of polling calls.

| Step | Caller | Endpoint | Count |
|---|---|---|---|
| 1. Presign | Frontend | `POST /batches/presign` | 1 per batch |
| 2. Upload | Frontend | Supabase Storage (direct PUT) | N per batch |
| 3. Confirm | Frontend | `POST /batches/{id}/confirm` | 1 per batch |
| 4. Status polling | Frontend | `GET /batches/{id}` | Variable (see §02.2.5) |
| 5. Document list | Frontend | `GET /batches/{id}/documents` | Optional |

Steps 1–3 are mandatory. Steps 4–5 are driven by the frontend polling or SSE strategy.

**The upload (step 2) goes directly to Supabase Storage — it does not pass through the API.** The API never receives file bytes.

---

## 02.2.2 External Service Calls per Batch

Each API call triggers downstream calls to storage and the database. This section maps every outbound call the API makes for a batch of N documents.

### POST /batches/presign

| Service | Operation | Count | Concurrency |
|---|---|---|---|
| PostgreSQL | `INSERT batches` | 1 | — |
| PostgreSQL | `INSERT documents` (bulk) | 1 (bulk, not N) | — |
| Supabase Storage | Generate presigned URL | N | Concurrent (`asyncio.TaskGroup`) |

The bulk insert writes all N document rows in a single statement. Presigned URL generation is the only per-document external call — done concurrently.

### POST /batches/{id}/confirm

| Service | Operation | Count | Concurrency |
|---|---|---|---|
| Supabase Storage | `HEAD` object key | N | Concurrent (`asyncio.TaskGroup`) |
| PostgreSQL | `UPDATE documents SET status = 'upload_confirmed'` | N | Sequential (single transaction) |
| Redis | `PUBLISH uploads.confirmed` | N | Sequential (post-transaction) |

Storage HEAD requests verify each object exists before any status update is written. All N HEAD requests are issued concurrently — total wall-clock time is bounded by the slowest individual HEAD, not N × HEAD latency.

### GET /batches/{id}

| Service | Operation | Count |
|---|---|---|
| PostgreSQL | `SELECT batches WHERE id = $1` | 1 |

Single PK lookup with RLS filter. No storage or Redis interaction.

### GET /batches/{id}/documents

| Service | Operation | Count |
|---|---|---|
| PostgreSQL | `SELECT documents WHERE batch_id = $1` | 1 (paginated) |

Paginated composite index scan. No storage or Redis interaction.

## 02.2.3 Call Amplification for a Batch of N Documents

For a batch of **N documents** from presign through confirmed (before processing begins):

| Phase | API calls | Storage calls | DB calls | Redis calls |
|---|---|---|---|---|
| Presign | 1 | N (presigned URL gen) | 2 (1 batch INSERT + 1 bulk doc INSERT) | — |
| Upload | — | N (direct PUT, bypasses API) | — | — |
| Confirm | 1 | N (HEAD verify) | N (UPDATE per doc) | N (PUBLISH per doc) |
| **Total** | **2** | **3N** | **N + 2** | **N** |

**Grand total external calls: 5N + 2** before processing begins (excluding polling).

At 500 documents per batch (the API maximum): **2,502 external calls** to initiate the batch.

### Comparison with per-document confirm (rejected design)

If the frontend had confirmed per document as each upload completed, the call pattern would be:

| Phase | API calls | Storage calls | DB calls | Redis calls |
|---|---|---|---|---|
| Presign | 1 | N | 2 | — |
| Upload + Confirm (interleaved) | N | 2N | N | N |
| **Total** | **N + 1** | **3N** | **N + 2** | **N** |

The external service calls are identical. The only difference is API calls: **N+1** per-document confirms vs. **2** batch confirms. The batch design was chosen for client simplicity (see ADR-005 in §02.1.2).

## 02.2.4 What Is Triggered When

End-to-end call map from batch creation to queue entry.

```
Frontend submits batch
  → POST /batches/presign
      DB: INSERT batches (1 row)
      DB: INSERT documents × N (1 bulk statement)
      Storage: generate presigned URL × N   ← concurrent
      Response: batch_id + N × {document_id, upload_url, object_key}

Frontend uploads files
  → PUT {upload_url} × N                    ← concurrent, direct to Supabase Storage
      (API is not involved)

Frontend confirms batch
  → POST /batches/{id}/confirm
      Storage: HEAD {object_key} × N        ← concurrent
      For each object found:
        DB: UPDATE documents SET status = 'upload_confirmed'
        Redis: PUBLISH uploads.confirmed {document_id, batch_id}
      For each object not found:
        DB: UPDATE documents SET status = 'failed', error_reason = 'object_not_found'
      Response: {confirmed: [...], failed: [...]}

Consumer receives events (per document, in invoice-pipeline)
  → Redis: subscribe uploads.confirmed
      DB: SELECT documents WHERE id = $1
      DB: UPDATE documents SET status = 'queued'
      DB: UPDATE batches SET queued_count + 1
      Redis: LPUSH queue.{xml|pdf|img}      ← Celery task
```

## 02.2.5 Polling Cost

The frontend polls `GET /batches/{id}` to track processing progress. Polling cost depends entirely on interval and batch duration.

### Cost model

| Polling interval | Batch duration | Polls per batch | DB reads |
|---|---|---|---|
| 2s | 30s | 15 | 15 |
| 2s | 5 min | 150 | 150 |
| 5s | 30s | 6 | 6 |
| 5s | 5 min | 60 | 60 |

Each poll is a single PK lookup — negligible cost individually. The concern is aggregate load under many concurrent active batches.

### Concurrent active batches

If K users are each polling one active batch at interval T seconds:

```
DB reads/second = K / T
```

At K=50 concurrent active batches and T=2s: **25 DB reads/second** from polling alone. This is within normal OLTP load for Supabase but worth monitoring as user count grows.

### Recommended intervals

| Scenario | Recommended interval | Reason |
|---|---|---|
| Batch < 10 documents | 1–2s | Fast processing, low latency matters |
| Batch 10–100 documents | 2–5s | Balance responsiveness and DB load |
| Batch > 100 documents | 5–10s | Processing takes > 30s, polling more often adds no value |

**SSE alternative:** `GET /batches/{id}` can be upgraded to Server-Sent Events to push status changes instead of polling. This eliminates unnecessary DB reads between state changes but requires a persistent connection per active batch. Not implemented in the initial version.

## 02.2.6 Presigned URL Expiry and Retry Cost

Presigned URLs returned by `POST /batches/presign` expire after a short window (15 minutes, configurable). If the frontend does not complete all uploads before expiry, subsequent PUT requests to Supabase Storage will return `403`.

When this happens, the frontend must call `POST /batches/presign` again for the expired documents to obtain fresh URLs. This reuses the existing `batch_id` and `document_id` values — it does not create new records.

| Scenario | Extra API calls | Extra DB writes | Extra Storage calls |
|---|---|---|---|
| All uploads complete before expiry | 0 | 0 | 0 |
| K documents expire, re-presigned once | 1 | 0 (UPDATE presigned_url, no new rows) | K |
| K documents expire, re-presigned twice | 2 | 0 | 2K |

Expiry is rare under normal conditions (15 minutes is generous for any batch ≤ 500 files). It becomes relevant on very slow connections or when the user pauses mid-upload.

---

## 02.2.7 Failed Document Cost

A document that fails verification during confirm (object not found in storage) does not enter the processing queue. It consumes:

- 1 storage HEAD request (to detect the missing object)
- 1 DB write (`UPDATE documents SET status = 'failed'`)
- 0 Redis publishes

Failed documents at confirm time do not consume worker resources. They are terminal — no retry, no DLQ entry. The client is responsible for re-uploading and re-confirming if needed.

## 02.2.8 Latency Targets

Performance targets for each API endpoint. These are p95 targets under normal load (one active batch of 500 documents).

### Response time by endpoint

| Endpoint | Target p95 | Bottleneck | Notes |
|---|---|---|---|
| `POST /batches/presign` (10 docs) | < 500ms | Storage URL generation × 10 concurrent | |
| `POST /batches/presign` (100 docs) | < 2s | Storage URL generation × 100 concurrent | |
| `POST /batches/presign` (500 docs) | < 5s | Storage URL generation × 500 concurrent | API maximum |
| `POST /batches/{id}/confirm` (10 docs) | < 300ms | Storage HEAD × 10 concurrent | |
| `POST /batches/{id}/confirm` (100 docs) | < 1s | Storage HEAD × 100 concurrent | |
| `POST /batches/{id}/confirm` (500 docs) | < 3s | Storage HEAD × 500 concurrent | API maximum |
| `GET /batches/{id}` | < 50ms | Single PK lookup | Polling hot path |
| `GET /batches/{id}/documents` | < 200ms | Composite index scan, paginated | |

### Scaling characteristics

`POST /batches/presign` and `POST /batches/{id}/confirm` both scale with N (documents per batch) but not linearly — both use `asyncio.TaskGroup` for concurrent external calls. The bottleneck is the slowest individual storage call, not N × average latency.

**What breaks these targets:**

- `asyncio.TaskGroup` not used — sequential storage calls multiply latency by N
- Storage in a different region than the API — cross-region HEAD requests add 50–150ms each
- Connection pool exhaustion — tasks queue behind pool waiters instead of running concurrently
- Large batches on cold API instances — first presigned URL generation includes TLS handshake to storage

### Downstream latency (not counted in API response time)

| Phase | Component | Typical duration |
|---|---|---|
| Consumer processes notification | Consumer | < 50ms per document |
| Worker picks up task | Celery | 0–5s (depends on queue depth) |
| Worker processes document | Worker | 1–30s (XML fast, image/PDF slow) |
| Full batch completes (100 docs) | End-to-end | 30s–5min |

The API response time is only the presign and confirm calls. The processing pipeline is fully asynchronous — the client polls for completion independently.
