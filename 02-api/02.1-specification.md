# 02.1 API — Technical Specification

## 02.1.1 Overview

The API is the HTTP entry point for all client interactions. It is responsible for receiving batch submissions, generating presigned upload URLs, recording document metadata, and serving batch status queries. It does not process documents and does not download files.

**Package:** `invoice-api`
**Framework:** FastAPI (Python 3.12)
**Deployment:** Railway or AWS ECS (same platform as workers)

---

## 02.1.2 Architecture Decision Records

### ADR-001 — FastAPI over Hono (TypeScript)

**Decision:** Use FastAPI (Python) instead of Hono (TypeScript/Node.js).

**Context:** The worker fleet is entirely Python (Celery, lxml, pdfplumber, Pillow). The API needs to publish Celery tasks to Redis.

**Reasons:**
- Publishing Celery tasks from TypeScript requires constructing raw Redis messages that mimic Celery's internal wire protocol. This protocol is undocumented and version-dependent. Any Celery upgrade can silently break TypeScript publishing with no compile-time signal.
- Pydantic models defined in `invoice-models` can be shared between the API and workers. With TypeScript, task payload schemas would be defined twice (Zod + Pydantic) and would drift.
- The entire backend — API, Consumer, workers — operates in one language with one CI pipeline, one linting configuration, and one dependency management tool.
- Nothing is implemented yet. Migration cost is zero.

**Consequences:** The Next.js frontend calls the FastAPI backend over HTTP, which is standard. TypeScript types for the API contract are generated from FastAPI's OpenAPI schema using `openapi-typescript` — no manual sync needed.

**What was rejected:** Keeping Hono for Vercel-native deployment. This argument disappears because the API must run on a long-lived server (Railway or ECS) due to ADR-004 below.

---

### ADR-002 — Frontend Uploads Directly to Supabase Storage via Presigned URLs

**Decision:** The API generates presigned URLs; the frontend uploads files directly to Supabase Storage without routing them through the API.

**Context:** Vercel serverless functions have a ~4.5 MB request body limit. Batch uploads of fiscal documents can easily exceed this. Even on Railway or ECS, proxying file uploads through the API adds latency and resource consumption with no benefit.

**Reasons:**
- Eliminates the API as a file proxy. The API handles only metadata (URLs, filenames, declared types).
- Prevents request body size limits from constraining batch size.
- Follows the standard pattern for object storage: generate a short-lived signed URL on the server, upload client-side.

**Consequences:** The API must generate presigned URLs and create the initial document record in the database before returning the URL to the frontend. The presigned URL must expire after a short window (e.g., 15 minutes).

---

### ADR-003 — Accept Object Keys, Not File URLs

**Decision:** The batch submission endpoint accepts Supabase Storage object keys (e.g., `{user_id}/{batch_id}/{doc_id}/filename.xml`), never arbitrary URLs.

**Context:** If the API accepts user-supplied URLs and downloads them (for Classifier inspection or any other reason), it becomes an open SSRF proxy. On Railway or AWS, cloud metadata endpoints (`169.254.169.254`, `fd00:ec2::254`) are reachable from application processes.

**Reasons:**
- An object key is a path within a known, trusted bucket. The API constructs the storage URL internally from a known base.
- An arbitrary URL can point to internal infrastructure, IAM metadata endpoints, or internal VPC services.
- This constraint is enforced at the API level. Workers also only operate on object keys from the known bucket.

**Consequences:** The frontend must use the object key returned with the presigned URL, not the full URL. The API validates that the submitted key matches the expected path pattern for the authenticated user.

---

### ADR-004 — Classifier Runs in invoice-processors, Not in the API Request Path

**Decision:** The API does not classify documents. It accepts the client-declared MIME type at presigned URL creation time, normalizes it to one of three internal types (`xml`, `pdf`, `img`), and stores it in the database. The Consumer reads this type and routes accordingly.

**Context:** Magic byte inspection requires downloading at least the first bytes of each file. Doing this synchronously inside the API request for every file in a batch is a blocking I/O operation. At ~30ms per file (same-region S3 GET), a 100-file batch adds 3 seconds to the API response. A 1,000-file batch would exceed any reasonable request timeout, and no tasks would ever reach Redis.

**Reasons:**
- The API responds immediately after recording metadata. No file downloads in the request path.
- The worker validates the actual file content against the declared type on pickup. If the declared type is wrong (mismatched magic bytes), the worker writes `failed` with reason `type_mismatch`. This is a terminal failure — no retry.
- Client-declared types are validated at the API level: only `image/*`, `application/pdf`, `application/xml`, and `text/xml` are accepted. Everything else is rejected with `422` before a presigned URL is issued.

**Consequences:** The system trusts the client's declared MIME type for routing, but verifies at the worker. A malicious or buggy client that declares the wrong type will have their document fail at the worker with a clear error reason, not silently.

## 02.1.3 Functional Requirements

### What the API does

1. **Presigned URL generation:** Accepts a list of file metadata objects (filename, declared MIME type, file size), validates each, creates document records in the database, and returns one presigned upload URL per document.

2. **Batch status query:** Returns the current processing status of a batch — total documents, how many are completed, how many failed, and the overall batch state.

3. **Document list query:** Returns per-document status within a batch, including error reasons for failed documents.

4. **Health check:** Returns service liveness for deployment orchestration.

### What the API does not do

- Download or inspect file contents
- Publish Celery tasks directly (that is the Consumer's responsibility)
- Process documents
- Serve file downloads (files are accessed directly from storage via signed URLs)

## 02.1.4 Endpoints

### POST /batches/presign

Creates a new batch and returns presigned upload URLs for each document.

**Request:**
```json
{
  "documents": [
    {
      "filename": "nota_fiscal.xml",
      "mime_type": "application/xml",
      "file_size": 48200
    }
  ]
}
```

**Validations (reject before creating any record):**
- `mime_type` must be one of: `image/jpeg`, `image/png`, `image/webp`, `image/tiff`, `application/pdf`, `application/xml`, `text/xml`
- `file_size` must be > 0 and ≤ 50 MB
- `documents` array must contain between 1 and 500 items
- All validations run before any record is written — partial batches are not created

**Response `202 Accepted`:**
```json
{
  "batch_id": "uuid",
  "documents": [
    {
      "document_id": "uuid",
      "upload_url": "https://...",
      "upload_url_expires_at": "ISO8601",
      "object_key": "{user_id}/{batch_id}/{document_id}/nota_fiscal.xml"
    }
  ]
}
```

**Error responses:**
- `401` — missing or invalid JWT
- `422` — validation failure (invalid MIME type, file too large, batch too large)
- `429` — queue backpressure limit reached (queue depth > high-water mark)
- `500` — database or storage error

---

### GET /batches/{batch_id}

Returns the current status of a batch.

**Response `200 OK`:**
```json
{
  "batch_id": "uuid",
  "status": "processing",
  "total": 10,
  "queued": 3,
  "processing": 2,
  "completed": 4,
  "failed": 1,
  "created_at": "ISO8601",
  "completed_at": null
}
```

**Batch status values:** `pending_upload` → `processing` → `completed` | `partial_failure` | `failed`

**Error responses:**
- `401` — unauthenticated
- `404` — batch not found or does not belong to the authenticated user

---

### GET /batches/{batch_id}/documents

Returns per-document status within a batch. Paginated.

**Query params:** `?page=1&page_size=50&status=failed`

**Response `200 OK`:**
```json
{
  "total": 10,
  "page": 1,
  "items": [
    {
      "document_id": "uuid",
      "filename": "nota_fiscal.xml",
      "doc_type": "xml",
      "status": "failed",
      "error_reason": "XSD validation failed: element 'infNFe' missing required attribute 'versao'",
      "created_at": "ISO8601",
      "updated_at": "ISO8601"
    }
  ]
}
```

---

### GET /health

Returns `200 OK` with no body. Used by Railway/ECS health checks.

## 02.1.5 Security Requirements

### Authentication (SEC-001 — CVSS 9.8)

Every endpoint except `/health` must require a valid JWT issued by Supabase Auth. The JWT is validated in FastAPI middleware before any request handler runs. An invalid or missing token returns `401` immediately — no partial processing.

Do not implement custom JWT validation logic. Use the Supabase Auth public key to verify the token signature.

### Tenant Isolation (SEC-002 — CVSS 9.1)

Every database query in the API must filter by the authenticated user's `user_id`. A user must never be able to retrieve another user's batch or document, even if they know the `batch_id` UUID.

Storage object keys must be prefixed with `{user_id}/`. A presigned URL generated for user A must only grant write access to paths under `user_id_A/`.

### SSRF via Object Keys (SEC-004 — CVSS 9.0)

The API accepts object keys from clients. Before generating a presigned URL or constructing any storage path from a client-supplied key, validate that the key matches the expected pattern:

```
^{authenticated_user_id}/{batch_id}/{document_id}/[a-zA-Z0-9._-]+$
```

Reject any key that does not match. Never construct a URL from an object key that could point outside the known bucket.

### Rate Limiting (SEC-005)

Apply per-user rate limiting on `POST /batches/presign` to prevent batch flooding. Suggested limit: 10 batch creation requests per minute per user. Return `429` when exceeded.

### CORS (SEC-016)

Restrict `Access-Control-Allow-Origin` to the Vercel frontend domain only. Do not use `*`. Configure this explicitly — FastAPI's default CORS middleware allows all origins if misconfigured.

### Input Limits (SEC-006)

Enforced at `POST /batches/presign`:
- Maximum file size: 50 MB per document
- Maximum documents per batch: 500
- Accepted MIME types: enumerated list only (see §02.1.4)

These limits are validated in the Pydantic request model using `Field(le=..., ge=...)` constraints. They run before any database write.

### Backpressure (PERF-008)

If the Redis queue depth exceeds a configured high-water mark, return `429` to the client instead of publishing more tasks. This prevents unbounded queue growth during worker outages.

### LGPD (SEC-017)

CNPJ/CPF values and financial amounts must never appear in API logs or error messages. Use `structlog` with a processor that scrubs known PII field names before output.

## 02.1.6 Performance Requirements

### Connection pools via lifespan (FW-003)

`asyncpg` (PostgreSQL) and `redis.asyncio` (Redis) connection pools must be created once per process in FastAPI's `lifespan` context manager and stored on `app.state`. Per-request connections exhaust file descriptors under any meaningful load.

```python
@asynccontextmanager
async def lifespan(app: FastAPI):
    app.state.db = await asyncpg.create_pool(DATABASE_URL, min_size=5, max_size=20)
    app.state.redis = await redis.asyncio.from_url(REDIS_URL)
    yield
    await app.state.db.close()
    await app.state.redis.aclose()
```

### Database client (FW-013)

Use `asyncpg` directly for all database operations in the API. Do not use the Supabase Python client for database writes — it adds HTTP overhead and does not support connection pooling. Connect via Supabase's PgBouncer endpoint (`DATABASE_URL`, port 6543, transaction pooling mode) for all application queries.

### Redis client (FW-014)

Use `redis.asyncio` from `redis-py ≥ 5`. Do not use `aioredis` — it is merged into `redis-py` and the standalone package is abandoned.

### Response time targets

| Endpoint | Target p95 |
|---|---|
| `POST /batches/presign` (10 docs) | < 500ms |
| `POST /batches/presign` (100 docs) | < 2s |
| `GET /batches/{id}` | < 100ms |
| `GET /batches/{id}/documents` | < 200ms |

Batch presign time scales with the number of documents because each requires a presigned URL generation call to Supabase Storage. Use `asyncio.TaskGroup` to generate all presigned URLs concurrently, not sequentially.

## 02.1.7 Testing Requirements

### Must pass before any deployment

**T-CRIT-001 — Every endpoint returns 401 without a valid JWT**
Test every route individually. A missing middleware registration is a silent full exposure.

**T-CRIT-006 — Cross-tenant isolation**
Create two users. User A creates a batch. User B's token must receive `404` on `GET /batches/{user_a_batch_id}` and `GET /batches/{user_a_batch_id}/documents`.

### High priority

**T-HIGH-002 — Object key validation rejects invalid patterns**
Submit keys containing `../`, absolute paths, keys from another user's prefix, and keys pointing outside the expected bucket structure. All must return `422`.

**T-HIGH-006 — Response time under batch load**
Measure `POST /batches/presign` at 1, 10, 100, and 500 documents. Establish the threshold at which presigned URL generation becomes the bottleneck.

**T-HIGH-007 — Backpressure returns 429**
Artificially raise Redis queue depth above the high-water mark. Submit a batch. Assert `429` is returned and no database records are created.

### Integration tests

Use `testcontainers-python` for PostgreSQL. Use a real Redis instance (not mocked) to verify `asyncio.TaskGroup` concurrency and connection pool behavior under load.

## 02.1.8 Implementation Notes

### Dependency management (FW-009)

Use `uv` for package management. The `invoice-api` package is a workspace member in the monorepo `uv` workspace alongside `invoice-models`, `invoice-processors`, and `invoice-pipeline`.

### Python version (FW-017)

Python 3.12. Use `asyncio.TaskGroup` for concurrent presigned URL generation. Pin FastAPI ≥ 0.111 for Pydantic v2 compatibility.

### OpenAPI and TypeScript types

FastAPI generates an OpenAPI schema at `/openapi.json`. Run `openapi-typescript` in the frontend CI to regenerate TypeScript types on every API change. This replaces any manual type definitions in the Next.js codebase.

### Structured logging

Use `structlog` with JSON output. Bind `user_id`, `batch_id`, and `request_id` to every log line via `contextvars`. Never log CNPJ, CPF, or financial amounts.

### Secrets

## 02.1.9 What Not To Do

**Do not download files in any API endpoint.**
The API processes metadata only. Any file download — even a range request for magic byte inspection — is a blocking I/O operation in the request path and an SSRF vector.

**Do not accept arbitrary URLs from clients.**
Only accept object keys. The storage base URL is constructed server-side from a known, trusted value.

**Do not use the Supabase Python client for database writes.**
It uses HTTP under the hood. Use `asyncpg` directly for all queries.

**Do not create connection pools outside the lifespan context.**
Pools created at module import time are not properly closed on shutdown and cannot be configured per-deployment.

**Do not use `*` for CORS origins.**
Restrict to the Vercel frontend domain. A misconfigured CORS policy on an authenticated API is a CSRF vector.

**Do not log request bodies or file metadata fields that may contain PII.**
`filename` fields sometimes contain CNPJ values (e.g., `NF_12345678000195.xml`). Log only `document_id`, `batch_id`, and `doc_type`.

**Do not return 500 errors with internal details to the client.**
Use a global exception handler that returns a generic error response and logs the full traceback internally.

**Do not publish Celery tasks from the API.**
The Consumer is responsible for publishing tasks after confirming the upload is complete. The API only creates the document record and returns the presigned URL. This separation prevents tasks from being published for files that were never successfully uploaded.

**Do not skip input validation for batch size and file size.**
A client submitting 10,000 documents in a single batch or a 500MB file declaration is either a bug or an attack. Both must be rejected at the Pydantic model level before any database interaction.
