# 05.1 Database Schema

## 05.1.1 Overview

Production-ready PostgreSQL schema for the SEFAZ fiscal document processing system, hosted on Supabase PostgreSQL with PgBouncer in transaction pooling mode. All tables live in the `public` schema and use Row-Level Security (RLS) for tenant isolation.

---

## 05.1.2 Architecture Decision Records

### ADR-001 — CHECK Constraints over ENUM Types for Status Fields

**Decision:** Use `CHECK (status IN (...))` constraints instead of `CREATE TYPE ... AS ENUM`.

**Context:** PostgreSQL enums cannot have values removed. Adding a value requires `ALTER TYPE ... ADD VALUE`, which cannot run inside a transaction. Renaming or reordering values is painful and deployment-risky.

**Reasons:**
- CHECK constraints can be dropped and recreated in a single migration transaction.
- Status values will evolve as the pipeline matures (e.g., adding `cancelled`, `retrying`).
- Avoids a class of migration failures when deploying schema changes.

**Consequences:** Status values are not enforced at the type level — they are enforced at the constraint level. The application layer (Pydantic models) provides compile-time safety. The database provides runtime safety.

---

### ADR-002 — TEXT over VARCHAR(n)

**Decision:** Use `TEXT` for all string columns. No `VARCHAR(n)` anywhere.

**Context:** In PostgreSQL, `TEXT` and `VARCHAR(n)` have identical storage and performance characteristics. The only difference is the length check, which provides a false sense of safety and creates migration friction when limits need to change.

**Reasons:**
- Changing `VARCHAR(255)` to `VARCHAR(512)` requires `ALTER COLUMN ... TYPE`, which takes an `ACCESS EXCLUSIVE` lock on the table.
- Application-level validation (Pydantic `Field(max_length=...)`) is the correct place for input length limits.
- PostgreSQL documentation explicitly states there is no performance difference.

**Consequences:** Length validation happens in the API layer, not the database. The database stores whatever the application sends.

---

### ADR-003 — Denormalized user_id on documents for RLS Performance

**Decision:** `documents.user_id` is denormalized (duplicated from `batches.user_id`) to avoid a JOIN in the RLS policy.

**Context:** Without `documents.user_id`, the RLS policy on `documents` would require `WHERE batch_id IN (SELECT id FROM batches WHERE user_id = auth.uid())`. This subquery runs on every row access — every SELECT, UPDATE, and DELETE. For a user with thousands of documents across many batches, this becomes a performance bottleneck.

**Reasons:**
- A direct `WHERE user_id = auth.uid()` on `documents` is a simple index lookup.
- The denormalization is safe: `user_id` never changes after document creation, so there is no update anomaly.
- The storage cost is 16 bytes (UUID) per document row — negligible.

**Consequences:** The application must set `documents.user_id` at INSERT time. A foreign key on `documents.user_id` referencing `users.id` provides referential integrity.

---

### ADR-004 — PgBouncer Transaction Pooling Compatibility

**Decision:** The schema and all queries must be compatible with PgBouncer in transaction pooling mode.

**Context:** Supabase routes application connections through PgBouncer in transaction mode. In this mode, a server-side connection is assigned to a client only for the duration of a transaction. Session-level state is lost between transactions.

**Prohibited features:**
- `PREPARE` / `DEALLOCATE` (named prepared statements — `$1` parameterized queries via client libraries are fine)
- `SET LOCAL` outside an explicit transaction block
- `LISTEN` / `NOTIFY` (use via direct connection only)
- `ADVISORY LOCK` (released at session end, which is unpredictable in transaction mode)
- Temporary tables (dropped at session end)

**Consequences:** All worker and API queries use simple parameterized queries. Migrations run against the direct connection URL (`DATABASE_DIRECT_URL`, port 5432), not the PgBouncer endpoint.

---

### ADR-005 — Atomic Batch Counters over COUNT Queries

**Decision:** Batch completion progress is tracked via atomic counter columns (`queued_count`, `completed_count`, `failed_count`) rather than derived via `SELECT COUNT(*) FROM documents WHERE batch_id = $1 AND status = 'completed'`.

**Context:** The batch status endpoint is polled repeatedly by the frontend during processing. A COUNT query on documents scans matching rows on every request.

**Reasons:**
- `UPDATE batches SET completed_count = completed_count + 1 WHERE id = $1` is a single row update — O(1) regardless of batch size.
- The RETURNING clause (`RETURNING completed_count + failed_count = total_documents AS is_complete`) eliminates a separate SELECT to check batch completion.
- Counter increments from concurrent workers are serialized by PostgreSQL's row-level locking — no application-level locks needed.

**Consequences:** Counters can drift from the true document count if a bug causes a double increment or a missed increment. The `CHECK (completed_count + failed_count <= total_documents)` constraint prevents over-counting. A periodic reconciliation job can correct undercounts if needed.

## 05.1.3 Complete DDL

### Extensions

```sql
-- gen_random_uuid() is available natively in PG15 (Supabase).
-- No extension needed. moddatetime is used for automatic updated_at.
CREATE EXTENSION IF NOT EXISTS moddatetime SCHEMA extensions;
```

### users

```sql
CREATE TABLE public.users (
    id          UUID PRIMARY KEY REFERENCES auth.users (id) ON DELETE CASCADE,
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);

COMMENT ON TABLE public.users IS
    'Application profile extending Supabase auth.users. Created on first sign-in.';

CREATE TRIGGER set_users_updated_at
    BEFORE UPDATE ON public.users
    FOR EACH ROW
    EXECUTE FUNCTION extensions.moddatetime(updated_at);
```

### batches

```sql
CREATE TABLE public.batches (
    id                UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id           UUID NOT NULL REFERENCES public.users (id) ON DELETE CASCADE,
    status            TEXT NOT NULL DEFAULT 'pending_upload',
    total_documents   INTEGER NOT NULL,
    queued_count      INTEGER NOT NULL DEFAULT 0,
    completed_count   INTEGER NOT NULL DEFAULT 0,
    failed_count      INTEGER NOT NULL DEFAULT 0,
    created_at        TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at        TIMESTAMPTZ NOT NULL DEFAULT now(),

    -- Status machine: only valid states
    CONSTRAINT batches_status_check CHECK (
        status IN ('pending_upload', 'processing', 'completed', 'partial_failure', 'failed')
    ),

    -- total_documents must be at least 1
    CONSTRAINT batches_total_documents_positive CHECK (total_documents >= 1),

    -- Counters must not be negative
    CONSTRAINT batches_queued_count_non_negative CHECK (queued_count >= 0),
    CONSTRAINT batches_completed_count_non_negative CHECK (completed_count >= 0),
    CONSTRAINT batches_failed_count_non_negative CHECK (failed_count >= 0),

    -- Counters must not exceed total
    CONSTRAINT batches_counters_within_total CHECK (
        completed_count + failed_count <= total_documents
    ),
    CONSTRAINT batches_queued_within_total CHECK (
        queued_count <= total_documents
    )
);

COMMENT ON TABLE public.batches IS
    'A batch groups documents submitted together in a single upload request.';

-- FK index: user_id (PostgreSQL does not auto-index FK columns)
CREATE INDEX idx_batches_user_id ON public.batches (user_id);

-- updated_at trigger
CREATE TRIGGER set_batches_updated_at
    BEFORE UPDATE ON public.batches
    FOR EACH ROW
    EXECUTE FUNCTION extensions.moddatetime(updated_at);
```

### documents

```sql
CREATE TABLE public.documents (
    id                    UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    batch_id              UUID NOT NULL REFERENCES public.batches (id) ON DELETE CASCADE,
    user_id               UUID NOT NULL REFERENCES public.users (id) ON DELETE CASCADE,
    original_filename     TEXT NOT NULL,
    s3_key                TEXT NOT NULL,
    file_size             INTEGER NOT NULL,
    doc_type              TEXT NOT NULL,
    status                TEXT NOT NULL DEFAULT 'pending_upload',
    extracted_data        JSONB,
    error_reason          TEXT,
    retry_count           INTEGER NOT NULL DEFAULT 0,
    created_at            TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at            TIMESTAMPTZ NOT NULL DEFAULT now(),
    processing_started_at TIMESTAMPTZ,
    completed_at          TIMESTAMPTZ,

    -- Document type: must be one of the three pipeline branches
    CONSTRAINT documents_doc_type_check CHECK (
        doc_type IN ('xml', 'pdf', 'img')
    ),

    -- Status machine: only valid states
    CONSTRAINT documents_status_check CHECK (
        status IN ('pending_upload', 'upload_confirmed', 'queued', 'processing', 'completed', 'failed')
    ),

    -- file_size must be positive (API enforces <= 50 MB)
    CONSTRAINT documents_file_size_positive CHECK (file_size > 0),

    -- retry_count must not be negative
    CONSTRAINT documents_retry_count_non_negative CHECK (retry_count >= 0),

    -- extracted_data must be a JSON object when present
    CONSTRAINT documents_extracted_data_is_object CHECK (
        extracted_data IS NULL OR jsonb_typeof(extracted_data) = 'object'
    ),

    -- s3_key must not be empty
    CONSTRAINT documents_s3_key_not_empty CHECK (s3_key <> ''),

    -- original_filename must not be empty
    CONSTRAINT documents_filename_not_empty CHECK (original_filename <> '')
);

COMMENT ON TABLE public.documents IS
    'Individual fiscal document within a batch. Status tracks pipeline progress.';

-- Primary query pattern: paginated documents by batch filtered by status
CREATE INDEX idx_documents_batch_id_status ON public.documents (batch_id, status);

-- RLS policy: fast user_id lookup for row-level security
CREATE INDEX idx_documents_user_id ON public.documents (user_id);

-- FK index: batch_id is already covered by the composite index above.
-- A standalone batch_id index is unnecessary — the composite (batch_id, status)
-- satisfies lookups on batch_id alone (leftmost prefix rule).

-- updated_at trigger
CREATE TRIGGER set_documents_updated_at
    BEFORE UPDATE ON public.documents
    FOR EACH ROW
    EXECUTE FUNCTION extensions.moddatetime(updated_at);
```

## 05.1.4 Row-Level Security Policies

RLS is enabled on all three tables. Workers and the Consumer connect using the Supabase service role key, which bypasses RLS entirely. The API and frontend use the user's JWT, which sets `auth.uid()`.

```sql
-- ============================================================
-- users
-- ============================================================
ALTER TABLE public.users ENABLE ROW LEVEL SECURITY;

-- Users can read their own profile
CREATE POLICY users_select_own ON public.users
    FOR SELECT
    USING (id = auth.uid());

-- Users can insert their own profile (first sign-in)
CREATE POLICY users_insert_own ON public.users
    FOR INSERT
    WITH CHECK (id = auth.uid());

-- Users can update their own profile
CREATE POLICY users_update_own ON public.users
    FOR UPDATE
    USING (id = auth.uid())
    WITH CHECK (id = auth.uid());

-- ============================================================
-- batches
-- ============================================================
ALTER TABLE public.batches ENABLE ROW LEVEL SECURITY;

-- Users can read their own batches
CREATE POLICY batches_select_own ON public.batches
    FOR SELECT
    USING (user_id = auth.uid());

-- Users can create batches for themselves
CREATE POLICY batches_insert_own ON public.batches
    FOR INSERT
    WITH CHECK (user_id = auth.uid());

-- Users can update their own batches (status polling, not worker writes)
-- Workers bypass RLS via service role.
CREATE POLICY batches_update_own ON public.batches
    FOR UPDATE
    USING (user_id = auth.uid())
    WITH CHECK (user_id = auth.uid());

-- ============================================================
-- documents
-- ============================================================
ALTER TABLE public.documents ENABLE ROW LEVEL SECURITY;

-- Users can read their own documents (uses idx_documents_user_id)
CREATE POLICY documents_select_own ON public.documents
    FOR SELECT
    USING (user_id = auth.uid());

-- Users can create documents for themselves
CREATE POLICY documents_insert_own ON public.documents
    FOR INSERT
    WITH CHECK (user_id = auth.uid());

-- Users can update their own documents (upload confirmation)
-- Workers bypass RLS via service role.
CREATE POLICY documents_update_own ON public.documents
    FOR UPDATE
    USING (user_id = auth.uid())
    WITH CHECK (user_id = auth.uid());
```

## 05.1.5 Key Query Patterns

### 1. Fetch one batch by id (API — user-scoped via RLS)

```sql
SELECT id, status, total_documents, queued_count, completed_count, failed_count,
       created_at, updated_at
FROM batches
WHERE id = $1;
-- RLS automatically appends: AND user_id = auth.uid()
-- Uses: PRIMARY KEY index on batches(id)
```

### 2. Paginated documents for a batch filtered by status (API)

```sql
SELECT id, original_filename, doc_type, status, error_reason,
       created_at, updated_at, completed_at
FROM documents
WHERE batch_id = $1 AND status = $2
ORDER BY created_at
LIMIT $3 OFFSET $4;
-- RLS automatically appends: AND user_id = auth.uid()
-- Uses: idx_documents_batch_id_status (batch_id, status)
```

### 3. Worker status transition to processing (service role — bypasses RLS)

```sql
UPDATE documents
SET status = 'processing',
    processing_started_at = now(),
    retry_count = $2
WHERE id = $1;
```

### 4. Worker result write — idempotent upsert (service role)

```sql
INSERT INTO documents (id, batch_id, user_id, original_filename, s3_key,
                        file_size, doc_type, status, extracted_data, completed_at)
VALUES ($1, $2, $3, $4, $5, $6, $7, 'completed', $8, now())
ON CONFLICT (id) DO UPDATE SET
    status         = EXCLUDED.status,
    extracted_data = EXCLUDED.extracted_data,
    completed_at   = EXCLUDED.completed_at,
    retry_count    = documents.retry_count;
```

### 5. Atomic batch counter increment + completion check (service role)

```sql
UPDATE batches
SET completed_count = completed_count + 1,
    updated_at = now()
WHERE id = $1
RETURNING completed_count + failed_count = total_documents AS is_complete;
```

### 6. Batch status finalization (service role — after is_complete = true)

```sql
UPDATE batches
SET status = CASE
    WHEN failed_count = 0 THEN 'completed'
    WHEN completed_count = 0 THEN 'failed'
    ELSE 'partial_failure'
END,
    updated_at = now()
WHERE id = $1;
```

## 05.1.6 Index Strategy

| Index | Columns | Purpose |
|---|---|---|
| `batches_pkey` | `(id)` | Primary key lookup for batch status queries |
| `idx_batches_user_id` | `(user_id)` | FK index + RLS policy evaluation on batches |
| `documents_pkey` | `(id)` | Primary key lookup for worker updates |
| `idx_documents_batch_id_status` | `(batch_id, status)` | Paginated document listing filtered by status within a batch |
| `idx_documents_user_id` | `(user_id)` | RLS policy evaluation — avoids sequential scan on `user_id = auth.uid()` |

**Indexes not created (and why):**

- **`(batch_id)` standalone on documents:** Redundant. The composite `(batch_id, status)` satisfies batch_id-only lookups via the leftmost prefix rule.
- **GIN index on `extracted_data`:** Not needed. The application does not query inside the JSONB structure — it reads the entire object. A GIN index would slow writes with no read benefit.
- **`(status)` standalone on documents:** Low cardinality (6 values). A status-only query would not be selective enough to benefit from a B-tree index. The composite `(batch_id, status)` handles the actual query pattern.
- **Partial index on `status = 'failed'`:** Could be added later if a monitoring dashboard needs to query all failed documents across batches. Not needed for the current access patterns.

## 05.1.7 Trade-offs and Notes

### file_size as INTEGER vs BIGINT

`INTEGER` supports up to ~2.1 GB. The API enforces a 50 MB per-document limit. `INTEGER` is sufficient and uses 4 bytes instead of 8. If the limit ever exceeds 2 GB, change to `BIGINT`.

### ON DELETE CASCADE on all foreign keys

Deleting a user cascades to batches, which cascades to documents. This is intentional for LGPD/GDPR right-to-erasure compliance. A single `DELETE FROM users WHERE id = $1` cleanly removes all user data. In production, this should be a controlled operation behind an admin endpoint, not exposed to regular users.

### moddatetime extension for updated_at

Supabase includes the `moddatetime` extension. Using a trigger is more reliable than relying on the application to set `updated_at` on every UPDATE — especially when workers, the Consumer, and the API all write to the same tables.

### No LISTEN/NOTIFY

The pipeline spec (04.1) mentions Supabase Realtime for frontend notifications on batch completion. Supabase Realtime works via its own internal replication mechanism, not `LISTEN/NOTIFY` through PgBouncer. The schema does not use `LISTEN/NOTIFY` anywhere — it would break under transaction pooling.

### Counter consistency guarantee

The CHECK constraint `completed_count + failed_count <= total_documents` prevents over-counting but cannot detect under-counting (a missed increment). If the system suspects counter drift, a reconciliation query can correct it:

```sql
UPDATE batches b
SET completed_count = (SELECT count(*) FROM documents WHERE batch_id = b.id AND status = 'completed'),
    failed_count    = (SELECT count(*) FROM documents WHERE batch_id = b.id AND status = 'failed')
WHERE id = $1;
```

This should run as an operational tool, not in the hot path.

### No separate extracted_fields table

Extracted fiscal data is stored as a JSONB column on `documents` rather than in a normalized child table. Reasons:
- The extracted fields vary by document type (XML NFe fields differ from image-extracted fields).
- The application reads and writes the entire extraction result as a unit — never individual fields.
- JSONB is stored in a TOAST table when it exceeds ~2 KB, so it does not bloat the main heap for row scans that do not reference `extracted_data`.

If analytical queries on extracted fields become necessary (e.g., "total value of all invoices this month"), a materialized view or a separate analytics table populated via a background job is the correct approach — not normalizing the JSONB into the transactional schema.
