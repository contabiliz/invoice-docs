# 05.4 Database Performance Reference

Concrete write counts, index coverage, connection sizing, contention analysis, vacuum pressure, and latency targets for the full schema. Use this as a cost model when planning capacity or evaluating schema changes.

---

## 05.4.1 Write Operations per Document (Happy Path)

Every document that enters the system and completes successfully produces exactly **8 database writes** plus at most 1 shared write on the batch row.

| Step | Writer | Table | Operation |
|---|---|---|---|
| 1. Batch presign | API | `documents` | `INSERT` (one row per document, bulk) |
| 2. Upload confirmed | API | `documents` | `UPDATE status = 'upload_confirmed'` |
| 3. Consumer queues task | Consumer | `documents` | `UPDATE status = 'queued'` |
| 4. Consumer increments counter | Consumer | `batches` | `UPDATE queued_count = queued_count + 1` |
| 5. Worker marks processing | Worker | `documents` | `UPDATE status = 'processing'` |
| 6. Worker writes result | Worker | `documents` | `UPSERT status = 'completed', extracted_data = …` |
| 7. Worker increments counter | Worker | `batches` | `UPDATE completed_count = completed_count + 1 RETURNING …` |
| 8. Batch finalization | Worker | `batches` | `UPDATE status = 'completed'` (last document only) |
| 9. Promotion job | Promotion job | `documents` | `UPDATE promoted_at = now()` |

Steps 1–7 and 9 happen for every promotable document. Step 8 happens once per batch. Documents without `chave_acesso` skip step 9.

**moddatetime trigger:** `documents` and `batches` both carry an `updated_at` trigger. Every `UPDATE` on these tables fires the trigger — adds one function call per write with negligible overhead, but worth counting: steps 2, 3, 5, 6, and 9 each fire the trigger on `documents`; steps 4, 7, and 8 fire it on `batches`.

## 05.4.2 Write Amplification for a Batch of N Documents

For a batch of **N documents**, all completing and being promoted successfully:

| Phase | Writes to `documents` | Writes to `batches` |
|---|---|---|
| Presign (bulk insert) | N | 1 |
| Upload confirmed | N | — |
| Consumer: queued | N | N |
| Worker: processing | N | — |
| Worker: result upsert | N | — |
| Worker: counter increment | — | N |
| Batch finalization | — | 1 |
| Promotion: promoted_at | N | — |
| **Total** | **6N** | **N + 2** |

**Grand total: 7N + 2 writes** for a clean batch of N documents (pipeline + promotion).

Pipeline only (before promotion): **5N + N + 2 = 6N + 2**.

At 500 documents per batch (the API maximum): **3,502 writes** end-to-end (including promotion).

### Failed documents

A document that exhausts retries and lands in the DLQ follows the same path through steps 1–5, then:
- DLQ worker writes `status = 'failed'` (1 write to `documents`)
- DLQ worker increments `failed_count` (1 write to `batches`)

Failed documents skip step 9 — `promoted_at` is never set for non-completed documents.

### Retried documents

Each Celery retry repeats steps 5–6 (worker picks up again). A document retried R times before completing produces **2R extra writes** to `documents` (one `processing` + one result per retry attempt).

## 05.4.3 What Is Triggered When

End-to-end event map from file upload to analytics availability.

```
User uploads files
  → POST /batches/presign
      DB: INSERT batches (1)
      DB: INSERT documents × N (bulk)

User confirms upload
  → POST /batches/{id}/confirm
      DB: UPDATE documents SET status = 'upload_confirmed' × N
      Redis: PUBLISH uploads.confirmed × N

Consumer receives upload event (per document)
  → reads doc_type from DB (SELECT documents WHERE id = $1)
  → DB: UPDATE documents SET status = 'queued'
  → DB: UPDATE batches SET queued_count = queued_count + 1
  → Redis: LPUSH queue.{xml|pdf|img} (Celery task)

Worker picks up task
  → DB: UPDATE documents SET status = 'processing'
  → Storage: GET file (S3 download)
  → processor.process(bytes)   ← no DB interaction
  → DB: UPSERT documents SET status = 'completed', extracted_data = …
  → DB: UPDATE batches SET completed_count = completed_count + 1
        RETURNING is_complete
  → if is_complete:
      DB: UPDATE batches SET status = 'completed|partial_failure|failed'
      Supabase Realtime: notifies frontend (via replication, not NOTIFY)

Promotion job (background, Phase 2)
  → SELECT documents WHERE status = 'completed' AND promoted_at IS NULL …
    (uses idx_documents_promotable — O(unpromoted) scan)
  → per document, in one transaction:
      DB: INSERT entidades × 2 ON CONFLICT DO NOTHING
      DB: INSERT invoices ON CONFLICT DO NOTHING
      DB: INSERT invoice_items × M (bulk, one per line item)
      DB: UPDATE documents SET promoted_at = now()
    (document exits idx_documents_promotable after commit)
```

## 05.4.5 Hot Row Contention

### batches table

All N workers processing the same batch will eventually `UPDATE batches SET completed_count = completed_count + 1` on the **same row**, concurrently.

PostgreSQL serializes these updates via row-level locking. Workers that arrive while the lock is held queue up and wait. This is correct behaviour, but creates a serialization bottleneck proportional to concurrency × lock hold time.

**Lock hold time:** The counter update modifies only `completed_count`, `updated_at` — columns that are not indexed on `batches`. PostgreSQL can use HOT (Heap Only Tuple) updates: no index pages need to be updated, only the heap. Lock hold time is sub-millisecond. At 500 sequential HOT updates, cumulative wait is under 500ms — acceptable. Note the asymmetry with `documents`: `status` is indexed there via `idx_documents_batch_id_status`, which disqualifies HOT for every status transition. On `batches`, `status` is not indexed — so the finalization `UPDATE batches SET status = ...` is also HOT-eligible, unlike the equivalent status writes on `documents`.

**When it becomes a concern:** A burst of very fast tasks (e.g., 500 trivial XML documents on 50 gevent greenlets) finishing within seconds. Contention window is short in absolute terms but measurable. If batch counter updates show lock wait times in `pg_stat_activity`, the mitigation is to decouple counter updates from task completion — e.g., batch the increments in the worker before flushing. For current load projections, this is not needed.

### entidades table

`entidades` has a different contention profile. `ON CONFLICT DO NOTHING` acquires a **share lock on the conflicting index tuple** before deciding to skip. If many promotion job runs (or a high-concurrency promotion job) attempt to insert the same CNPJ simultaneously, they contend on that index tuple.

Concretely: if the promotion job processes 100 documents from the same large supplier (same `cnpj_emitente`), 99 of the emitente upserts will conflict. Each conflict acquires an index tuple lock, checks the existing row, and releases it. These locks are held briefly and do not block reads, but they serialize against each other.

**Why this is bounded:** The promotion job is a background, rate-limited process — not a high-concurrency worker fleet. The serialization happens within a single job run, not across many concurrent processes. At typical promotion batch sizes (500 documents/run), the maximum contention is 500 consecutive index tuple locks on the same CNPJ — each sub-millisecond, total under 500ms.

**What would make this a real problem:** Running multiple concurrent promotion job instances against the same dataset, or running the promotion job at worker-level concurrency (50–100 parallelism). Neither is the current design. The promotion job is intentionally single-threaded.

## 05.4.6 Vacuum Pressure and Dead Tuple Accumulation

### Why documents accumulates dead tuples aggressively

Each `UPDATE` on a PostgreSQL row creates a dead tuple — the previous version of the row left in the heap until vacuumed. Every document passes through 5 status updates (steps 2, 3, 5, 6, and 9). That is **5 dead tuples per document** on the `documents` heap.

Critically: the `status` column is part of `idx_documents_batch_id_status`. Any update to an indexed column **disqualifies HOT updates** — each status transition creates a new heap tuple AND updates the index. Dead tuples accumulate at the full rate of updates.

| Batch size | Dead tuples on documents |
|---|---|
| 100 documents | ~500 |
| 500 documents | ~2,500 |
| 1,000 documents | ~5,000 |

### Autovacuum trigger threshold

PostgreSQL's default autovacuum threshold is `50 + 0.2 × live_row_count`. For a `documents` table with 10,000 live rows, autovacuum triggers when dead tuples exceed **2,050**. A single max-size batch (500 documents) generates 2,500 dead tuples — enough to trigger autovacuum after approximately one full batch cycle.

Autovacuum on Supabase runs with default settings. The threshold recalculates as the table grows:

| Live rows in documents | Autovacuum triggers at | Batches to trigger (500 docs each) |
|---|---|---|
| 1,000 | 250 dead tuples | < 1 batch |
| 10,000 | 2,050 dead tuples | ~1 batch |
| 100,000 | 20,050 dead tuples | ~8 batches |
| 1,000,000 | 200,050 dead tuples | ~80 batches |

At high row counts, the default threshold means autovacuum triggers less frequently relative to write volume. This is the well-known autovacuum scaling problem. Supabase Pro and Team tiers allow custom autovacuum parameters per table — if `pg_stat_user_tables` shows `n_dead_tup` growing steadily between vacuum runs, set:

```sql
ALTER TABLE public.documents SET (
    autovacuum_vacuum_scale_factor = 0.01,  -- trigger at 1% dead tuples instead of 20%
    autovacuum_vacuum_threshold = 50
);
```

This is not needed at launch but should be monitored once `documents` exceeds ~50,000 rows.

### batches: HOT updates reduce vacuum pressure

Unlike `documents`, the frequently-updated columns on `batches` (`completed_count`, `failed_count`, `queued_count`, `status`) are **not indexed**. PostgreSQL uses HOT updates: the new tuple version is written to the same heap page as the old one, and no index pages are touched. Dead tuples still accumulate in the heap, but at a lower page-churn rate and with no index bloat.

A batch of 500 documents generates 2N+1 = 1,001 dead tuples on its single `batches` row (one per counter update and finalization). These are all on the same heap page — autovacuum handles them in one pass.

### promoted_at and the partial index

Once a document is promoted, it exits `idx_documents_promotable`. The index automatically shrinks as documents are promoted — no manual maintenance needed. Vacuuming the partial index is faster than vacuuming a full index because only unpromoted rows are indexed.

## 05.4.7 Connection Pool Sizing

Workers use `psycopg3` in synchronous mode with **one persistent connection per OS process**, reused across all task executions in that process. This is not one connection per greenlet — gevent monkey-patches the socket layer so DB calls yield cooperatively, but they still serialize through the single connection.

### Connections per component (single instance)

| Component | Pool type | Client connections | Notes |
|---|---|---|---|
| API (FastAPI) | Async pool | 10 | Sized to uvicorn worker concurrency |
| Consumer | Single | 1 | One long-lived loop |
| worker-xml | gevent (50 greenlets) | 1 per OS process | Greenlets share one sync connection |
| worker-pdf | prefork (nproc processes) | nproc (typically 2–4) | Each process is independent |
| worker-img | gevent (100 greenlets) | 1 per OS process | Greenlets share one sync connection |
| worker-dlq | prefork (4 processes) | 4 | Low volume |
| Promotion job | Single | 1 | Background, one run at a time |

### Total connection budget (baseline deployment)

One instance of each component, worker-pdf on a 4-core host:

| Component | Client connections to PgBouncer |
|---|---|
| API | 10 |
| Consumer | 1 |
| worker-xml | 1 |
| worker-pdf | 4 |
| worker-img | 1 |
| worker-dlq | 4 |
| Promotion job | 1 |
| **Total** | **22** |

Scaling to two instances of each worker type:

| Component | Instances | Connections each | Total |
|---|---|---|---|
| API | 2 | 10 | 20 |
| Consumer | 1 | 1 | 1 |
| worker-xml | 2 | 1 | 2 |
| worker-pdf | 2 | 4 | 8 |
| worker-img | 4 | 1 | 4 |
| worker-dlq | 1 | 4 | 4 |
| Promotion job | 1 | 1 | 1 |
| **Total** | | | **40** |

### PgBouncer server-side connections (the real limit)

PgBouncer sits between the application and PostgreSQL. Client connections to PgBouncer (port 6543) are cheap. The constraint is **PgBouncer's server-side connection pool to PostgreSQL** — this is the number that Supabase tiers limit.

In transaction pooling mode, a client holds a server connection only for the duration of a transaction (typically <10ms per write). A worker-xml container with 1 client connection holds a server connection for roughly 1–5% of wall time. PgBouncer can multiplex many client connections over far fewer server connections.

**Practical implication:** The 40 client connections in the scaled deployment do not require 40 server-side PostgreSQL connections. PgBouncer pools them. Verify the effective server connection count against your Supabase tier's `pool_size` in the Supabase dashboard under Settings → Database. For the Pro tier (default `pool_size = 15` per database), 40 clients are well within reach at typical transaction durations.

**Never connect to port 5432 (direct) from workers or the API.** The direct connection bypasses PgBouncer and consumes a raw PostgreSQL connection against the hard tier limit. Reserve port 5432 exclusively for Alembic migrations.

## 05.4.8 Promotion Job Write Cost

For a promoted document with M line items:

| Write | Table | Operation | Count |
|---|---|---|---|
| Emitente upsert | `entidades` | `INSERT … ON CONFLICT DO NOTHING` | 1 |
| Destinatário upsert | `entidades` | `INSERT … ON CONFLICT DO NOTHING` | 1 |
| Invoice insert | `invoices` | `INSERT … ON CONFLICT DO NOTHING` | 1 |
| Item inserts | `invoice_items` | `INSERT … (bulk)` | M |
| Promotion flag | `documents` | `UPDATE promoted_at = now()` | 1 |

**Total: M + 4 writes per document**, all in one transaction.

For a typical NF-e with 10 line items: 14 writes. For a large NF-e with 100 items: 104 writes.

**Idempotency cost:** `ON CONFLICT DO NOTHING` on `entidades` and `invoices` reads the existing index before deciding to skip. For a document whose `chave_acesso` already exists in `invoices`, the write is a no-op but still acquires a brief index tuple lock. However, because `promoted_at` is set atomically in the same transaction, a successfully promoted document will never reach the promotion query again — re-processing the same document is only possible if the transaction rolled back, in which case the analytics rows were also rolled back.

## 05.4.9 RLS Evaluation Cost

RLS policies are evaluated on every row access — `SELECT`, `UPDATE`, `INSERT`, and `DELETE`. The cost depends entirely on whether the policy predicate can use an index.

| Table | RLS predicate | Index | Cost |
|---|---|---|---|
| `batches` | `user_id = auth.uid()` | `idx_batches_user_id` | Index lookup — O(log N) |
| `documents` | `user_id = auth.uid()` | `idx_documents_user_id` | Index lookup — O(log N) |
| `invoices` | `user_id = auth.uid()` | `idx_invoices_user_id` | Index lookup — O(log N) |
| `invoice_items` | `user_id = auth.uid()` | `idx_invoice_items_user_id` | Index lookup — O(log N) |
| `users` | `id = auth.uid()` | `users_pkey` | PK lookup — O(log N) |

Workers and the promotion job connect via the service role key, which bypasses RLS entirely. RLS overhead only applies to API requests and frontend queries.

**What would break RLS performance:** Removing the `user_id` index on any table, or adding a policy that requires a subquery (e.g., joining to another table to derive ownership). The current policies are deliberately kept to simple equality predicates — see `05.1` ADR-003.

## 05.4.10 Latency Targets

Performance targets for the hot paths. These are p99 targets under normal load, not averages. "Normal load" means a single batch of 500 documents actively processing.

### API endpoints

| Endpoint | Target p99 | Index path | Notes |
|---|---|---|---|
| `GET /batches/{id}` (status poll) | < 50 ms | `batches_pkey` → RLS `idx_batches_user_id` | PK + FK index, no joins |
| `GET /batches/{id}/documents` (list) | < 100 ms | `idx_documents_batch_id_status` | Composite, paginated with LIMIT |
| `POST /batches/presign` (bulk insert) | < 200 ms | — | N inserts to `documents`; N bounded by 500 |

### Worker database round-trips

| Operation | Target p99 | Notes |
|---|---|---|
| `UPDATE documents SET status = 'processing'` | < 20 ms | PK lookup, narrow write, HOT not available (status indexed) |
| `UPSERT documents SET extracted_data = …` | < 50 ms | TOAST write for JSONB payload; index update required |
| `UPDATE batches SET completed_count + 1 RETURNING` | < 10 ms | HOT update (counter not indexed), narrow row |
| `UPDATE batches SET status = …` (finalization) | < 10 ms | HOT update, fires once per batch |

### Promotion job

| Operation | Target p99 | Notes |
|---|---|---|
| Fetch batch of 500 unpromoted documents | < 100 ms | `idx_documents_promotable` partial index scan |
| Promote one document (M=10 items) | < 30 ms | 14 writes in one transaction |
| Full batch promotion (500 documents, M=10) | < 60 s | Sequential at ~120ms/doc including network RTT |

### Analytics queries

| Query | Target p99 | Notes |
|---|---|---|
| Supplier query (who bought from CNPJ X) | < 500 ms | Index on `cnpj_emitente` + `data_emissao` range + group |
| NCM breakdown for a buyer | < 500 ms | Index on `documento_destinatario` → join to `invoice_items` |
| Product code search | < 300 ms | Index on `codigo_produto` |

**When targets are missed:** Add `EXPLAIN (ANALYZE, BUFFERS)` to the slow query and compare against the index coverage map in §05.4.4. The most common causes are: RLS policy not using an index (missing `user_id` index), planner choosing a seq scan because statistics are stale (`ANALYZE` the table), or autovacuum lag causing bloated index pages (check `pg_stat_user_tables.n_dead_tup`).
