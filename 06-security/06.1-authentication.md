# 06.1 Authentication & Authorization

## 06.1.1 Overview

Authentication is handled entirely by Supabase Auth. The API validates JWTs on every request. Authorization is enforced at two layers: Row-Level Security policies in PostgreSQL for data access, and Supabase Storage policies for file access. Workers use a service role key that bypasses RLS — they are trusted internal processes, not user-facing actors.

---

## 06.1.2 Architecture Decision Records

### ADR-001 — Supabase Auth over Custom JWT

**Decision:** Use Supabase Auth as the identity provider. Do not implement custom JWT issuance or validation logic.

**Reasons:**
- Supabase Auth integrates directly with `auth.users`, which the `public.users` profile table extends. User creation, session management, and token refresh are handled out of the box.
- The `auth.uid()` function is available inside PostgreSQL RLS policies — no custom session variables or middleware tricks needed.
- Supabase Auth supports email/password, OAuth providers, and magic links without additional infrastructure.

**Consequences:** The API validates JWTs using Supabase's public JWT secret (`SUPABASE_JWT_SECRET`). This is a symmetric HMAC-SHA256 secret, not a public/private key pair. It must be treated as a credential and rotated on the standard schedule (every 180 days).

---

### ADR-002 — RLS as the Primary Authorization Boundary

**Decision:** Row-Level Security policies on PostgreSQL are the authoritative enforcement point for data isolation. Application-layer filtering (`WHERE user_id = current_user_id()`) is added as a defense-in-depth measure, not the primary control.

**Reasons:**
- RLS operates at the database level — it cannot be bypassed by application bugs, missing middleware, or new endpoints that forget to add a filter.
- `auth.uid()` is set by Supabase's connection infrastructure when using the anon or authenticated role. The service role bypasses all policies, which is the correct behavior for workers.
- A single misconfigured API endpoint cannot leak another tenant's data if RLS is in place.

**Consequences:** Every query from the API runs under the authenticated Supabase role, not the service role. Workers always use the service role connection string. These two connection strings must never be swapped.

---

### ADR-003 — Presigned URLs for Storage, Not Direct SDK Access

**Decision:** The frontend never holds long-lived storage credentials. All file uploads go through presigned URLs generated by the API. All file reads (if ever exposed to users) go through short-lived signed URLs.

**Reasons:**
- A presigned URL grants access to exactly one object for a limited time window. There are no credentials to steal and no broad permissions to escalate.
- Storage RLS policies restrict read access by `user_id` path prefix. A presigned URL for `user_a/batch_1/doc_1/file.xml` cannot be used to read `user_b/...`.
- The API validates that the requested path matches the authenticated user's prefix before generating the URL — no user can request a presigned URL for another user's path.

**Consequences:** The frontend makes two calls for each upload: one to the API for the presigned URL, one directly to Supabase Storage. The API call is fast (no file transfer). The storage call is a direct PUT — no API proxy in the data path.

---

### ADR-004 — Service Role for Workers, Authenticated Role for API

**Decision:** Workers and the Consumer connect to PostgreSQL and Supabase Storage using the Supabase service role key. The API uses the authenticated role via user JWTs.

**Reasons:**
- Workers process documents on behalf of users — they are not user sessions. They need to write to any row regardless of `user_id`. The service role is the correct tool for internal, trusted processes.
- Separating the two roles means a compromised API key does not give an attacker worker-level write access, and a compromised worker credential does not allow creating new batches on behalf of users.

**Consequences:** The service role key must never be sent to the frontend or logged. Rotation of this key requires redeploying all workers and the Consumer simultaneously.

---

### ADR-005 — Two Roles Only for v1 (User and Admin)

**Decision:** v1 implements two roles: `user` (default for all authenticated accounts) and `admin` (manually assigned). A third role `reader` (read-only access to own data, no upload) is deferred until there is a product requirement for it.

**Reasons:**
- Premature RBAC adds complexity without benefit. The product currently has one user type.
- Admin access is needed for DLQ review and operational queries. It should not share the same permissions as a regular submitter.
- Adding roles later via a `user_roles` table is low-cost. Removing over-engineered roles is not.

**Consequences:** Role is stored in the `public.users` table as a `TEXT` column with a CHECK constraint (`'user'` or `'admin'`). RLS policies check this column for admin-only operations. The admin role bypasses the `user_id = auth.uid()` filter on reads.

## 06.1.3 Authentication Flow

### Sign-in

```
Frontend                    Supabase Auth
    |                            |
    |-- POST /auth/v1/token ────→|
    |   { email, password }      |
    |←-- { access_token,         |
    |      refresh_token }  ─────|
```

The `access_token` is a JWT signed with `SUPABASE_JWT_SECRET`. It contains:
- `sub`: the user's UUID (`auth.users.id`)
- `role`: `authenticated`
- `exp`: expiry timestamp (default 1 hour)
- `email`: user's email

### API Request Authentication

Every request to the API (except `GET /health`) must include:

```
Authorization: Bearer <access_token>
```

FastAPI middleware validates the token before the request reaches any handler:

1. Extract the Bearer token from the `Authorization` header
2. Decode and verify the signature using `SUPABASE_JWT_SECRET`
3. Check `exp` — reject if expired
4. Extract `sub` (user UUID) and attach to the request state
5. If validation fails at any step: return `401 Unauthorized` immediately

The user UUID extracted from the JWT is used for all subsequent database queries and presigned URL path construction. It is never taken from the request body.

### Token Refresh

The frontend is responsible for token refresh using Supabase's client SDK. The API does not issue or refresh tokens — it only validates them. A `401` response from the API signals the frontend to refresh and retry.

## 06.1.4 Authorization Model

### Roles

| Role | Assigned by | Capabilities |
|---|---|---|
| `user` | Default on sign-up | Create batches, upload documents, view own data |
| `admin` | Manual DB update | All of the above + view all batches, access DLQ review endpoint |

Role is stored in `public.users.role`. It is not embedded in the JWT — the API reads it from the database on requests that require role checking.

### RLS Policies Summary

| Table | Policy | Condition |
|---|---|---|
| `users` | SELECT | `id = auth.uid()` |
| `users` | INSERT | `id = auth.uid()` |
| `users` | UPDATE | `id = auth.uid()` |
| `batches` | SELECT | `user_id = auth.uid()` OR role = `admin` |
| `batches` | INSERT | `user_id = auth.uid()` |
| `batches` | UPDATE | `user_id = auth.uid()` (API) — workers use service role |
| `documents` | SELECT | `user_id = auth.uid()` OR role = `admin` |
| `documents` | INSERT | `user_id = auth.uid()` |
| `documents` | UPDATE | `user_id = auth.uid()` (API) — workers use service role |

Admin SELECT policies use a helper function to avoid a subquery on every row:

```sql
CREATE OR REPLACE FUNCTION public.is_admin()
RETURNS boolean
LANGUAGE sql
SECURITY DEFINER
STABLE
AS $$
  SELECT role = 'admin' FROM public.users WHERE id = auth.uid();
$$;
```

```sql
-- Example: admin can see all batches
CREATE POLICY batches_select_admin ON public.batches
    FOR SELECT
    USING (user_id = auth.uid() OR public.is_admin());
```

### Tenant Isolation Guarantee

A user cannot access another user's data because:
1. All API queries run under the authenticated role — RLS `user_id = auth.uid()` filters apply
2. `documents.user_id` is denormalized — the RLS filter is a direct index lookup, not a join
3. Presigned URL paths are prefixed with `{auth.uid()}/` — the API validates this before generation
4. Workers write `user_id` on every INSERT — they receive it in the task payload from the Consumer, which read it from the database record created by the API

## 06.1.5 Storage Access Control

### Upload Flow

Files are never uploaded through the API. The frontend uploads directly to Supabase Storage using a presigned URL.

```
Object key format:  {user_id}/{batch_id}/{document_id}/{original_filename}

Example:            a1b2c3d4-.../e5f6.../g7h8.../nota_fiscal.xml
```

The API generates the presigned URL only after:
1. Verifying the authenticated user matches the `user_id` prefix
2. Creating the document record in the database
3. Confirming the object key matches the pattern `^{auth.uid()}/...`

A user cannot request a presigned URL for a path outside their own prefix.

### Supabase Storage Bucket Policy

The storage bucket is **private**. No public read access. Access is controlled by:
- Presigned URLs for upload (time-limited, single-object)
- Service role for worker downloads
- Signed URLs for any future user-facing file downloads (generated on demand, short expiry)

```
Bucket: invoice-documents
Access: private
RLS: enabled
```

Storage RLS policy (Supabase Storage uses its own policy syntax):

```sql
-- Users can upload to their own prefix only
CREATE POLICY "Users can upload own files"
ON storage.objects FOR INSERT
TO authenticated
WITH CHECK (
    bucket_id = 'invoice-documents'
    AND (storage.foldername(name))[1] = auth.uid()::text
);

-- Users can read their own files
CREATE POLICY "Users can read own files"
ON storage.objects FOR SELECT
TO authenticated
USING (
    bucket_id = 'invoice-documents'
    AND (storage.foldername(name))[1] = auth.uid()::text
);
```

## 06.1.6 Worker Credentials

Workers and the Consumer connect to both PostgreSQL and Supabase Storage using the service role key. This key bypasses all RLS policies.

### PostgreSQL

Workers connect via PgBouncer (transaction pooling mode) using `DATABASE_URL`. This connection authenticates as the `service_role` Postgres role.

Workers never receive a user JWT. They receive `user_id` as part of the Celery task payload (set by the Consumer from the database record). They use it to populate the `user_id` column on writes — they do not use it for authorization.

### Supabase Storage

Workers use the `SUPABASE_SERVICE_ROLE_KEY` to download files from storage. This key allows access to any object in any bucket regardless of RLS policies.

Workers only download objects whose `s3_key` was passed in the Celery task payload. They never construct storage paths from user input.

### Credential Scoping

| Component | Database connection | Storage access | Gemini API |
|---|---|---|---|
| API | Authenticated role (user JWT) | Presigned URL generation only | ✗ |
| Consumer | Service role | ✗ | ✗ |
| worker-xml | Service role | Download only (service key) | ✗ |
| worker-pdf | Service role | Download only (service key) | ✗ |
| worker-img | Service role | Download only (service key) | ✓ |
| worker-dlq | Service role | ✗ | ✗ |

`GEMINI_API_KEY` is scoped exclusively to `worker-img`. No other service receives it.

## 06.1.7 Secrets Inventory and Rotation

| Secret | Used by | Rotation interval |
|---|---|---|
| `SUPABASE_JWT_SECRET` | API (token validation) | 180 days |
| `SUPABASE_SERVICE_ROLE_KEY` | Consumer, all workers | 90 days |
| `DATABASE_URL` (PgBouncer) | API, Consumer, all workers | 30 days |
| `DATABASE_DIRECT_URL` (port 5432) | Alembic migrations only | 30 days |
| `REDIS_URL` (with AUTH password) | API, Consumer, all workers | 90 days |
| `GEMINI_API_KEY` | worker-img only | 90 days |

Secrets are stored in:
- **Railway:** Railway Service Variables, scoped per service
- **AWS ECS:** AWS Secrets Manager, injected via task definition `secrets` block

Secrets must never appear in:
- Application logs
- Error messages returned to clients
- Environment variable dumps
- Docker image layers
- Git history

## 06.1.8 What Not To Do

**Do not validate JWTs manually.**
Use the Supabase Auth library or a well-maintained JWT library with the `SUPABASE_JWT_SECRET`. Do not parse the token payload without verifying the signature first — an unverified JWT payload is attacker-controlled data.

**Do not use the service role key in the API.**
The API serves user requests. Using the service role would bypass all RLS policies and give the API (and any attacker who exploits it) unrestricted access to all tenant data.

**Do not use the authenticated role in workers.**
Workers process documents on behalf of users, not as users. A worker that authenticates as a user is limited to that user's RLS scope and cannot process documents for other users.

**Do not embed `user_id` in the JWT or trust client-provided user IDs.**
The `user_id` used for all operations is extracted from the validated JWT `sub` claim only. Any `user_id` value in the request body is ignored — a client cannot impersonate another user by sending a different `user_id` in the payload.

**Do not generate presigned URLs without validating the path prefix.**
Before calling Supabase Storage to generate a presigned URL, verify that the requested object key starts with `{auth.uid()}/`. A missing check here allows any authenticated user to generate upload URLs for other users' paths.

**Do not log the `Authorization` header or token values.**
Tokens are credentials. Logging them creates a credential exposure in the log aggregation system. Log only `user_id` (the UUID from the token, after validation).

**Do not share `GEMINI_API_KEY` across all worker services.**
XML and PDF workers have no reason to receive the Gemini API key. If a worker container is compromised, the blast radius is limited to what credentials it holds.

**Do not skip the `public.users` profile row check.**
The first time a user authenticates, their profile row in `public.users` must be created. If it does not exist, `is_admin()` will return NULL (not false), and RLS policy evaluation on admin-gated resources will behave unexpectedly. Create the profile row on first sign-in via a Supabase Auth hook or the first API request.
