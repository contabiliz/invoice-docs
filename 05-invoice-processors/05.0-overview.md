# 05.0 invoice-processors: Overview

## 05.0.1 Purpose

`invoice-processors` is a pure Python library that receives raw file bytes and returns structured fiscal data. It has no knowledge of Celery, Redis, database connections, or HTTP. Its single responsibility is document parsing and data extraction.

This boundary is intentional: it makes the extraction logic independently testable, reusable across different orchestration systems, and free of infrastructure concerns.

---

## 05.0.2 Package Contract

All three processor branches expose the same interface:

```python
from invoice_models.extraction import ExtractionResult

def process(content: bytes) -> ExtractionResult:
    ...
```

`ExtractionResult` is defined in `invoice-models` and is the only type that crosses the package boundary back to `invoice-pipeline`. Workers call `process()`, receive an `ExtractionResult`, and write it to the database — they do not parse or inspect the extraction output themselves.

---

## 05.0.3 The Three Branches

| Branch | Input | Primary library | Fallback | AI |
|---|---|---|---|---|
| **XML** | NF-e XML (SEFAZ schema) | lxml | — | No |
| **PDF** | DANFE PDF or scanned PDF | pdfplumber + PyMuPDF | pdf2image → image branch | No |
| **Image** | Thermal receipt image | Pillow | — | Gemini API |

### XML (`05.1`)

Validates the NF-e XML against the SEFAZ XSD schema, then extracts fields via XPath. No AI. No fallback. If XSD validation fails, the document is terminal-failed immediately — it is not a retryable error. XPath paths are fixed by law (SEFAZ publishes and maintains the schema).

### PDF (`05.2`)

Uses two complementary libraries:

- **pdfplumber**: Extracts text words with bounding boxes. Native table extraction.
- **PyMuPDF**: Extracts vector drawing edges and computes cell vertices from their intersections.

The combined data enables spatial reasoning: locating field labels in the document, finding their associated values by geometric proximity, and extracting table rows bounded by the document's drawn grid lines.

If extracted text falls below a confidence threshold (too few words, mostly unreadable), the document is classified as a scanned PDF and routed to the image branch.

### Image (`05.3`)

Applies Pillow preprocessing (resize, contrast enhancement for thermal paper) then calls the Gemini API in structured output mode. The Gemini response is validated by Pydantic before any result is returned. This branch is the most expensive and slowest — it is used only when text extraction is not possible.

---

## 05.0.4 Dependency Direction

```
invoice-pipeline
    └── invoice-processors   (calls process(), receives ExtractionResult)
            └── invoice-models   (ExtractionResult and field types only)
```

`invoice-processors` depends on `invoice-models` for output types. It does not depend on `invoice-pipeline`. `invoice-pipeline` depends on both.

---

## 05.0.5 Package Constraints

`invoice-processors` must never import:

- `celery` — no task definitions or workers
- `asyncpg` / `sqlalchemy` / any DB client — no database access
- `httpx` / `aiohttp` / any HTTP client — no outbound requests (except Gemini SDK, image branch only)
- `redis` — no broker access
- `boto3` / `supabase` — no storage access; it receives `bytes`, not paths

File I/O is allowed only via `tempfile` (in-memory or tmpfs) for intermediate conversion steps. Workers download files and pass `bytes`; processors never construct storage paths.

---

## 05.0.6 Testing Strategy

Because `invoice-processors` is pure Python with no infrastructure dependencies, it is the easiest layer to test thoroughly.

**Unit tests**: Each processing stage (adapter, candidate finder, validator, scorer) tested in isolation with fixture bytes.

**Integration tests**: Full `process(bytes) → ExtractionResult` tested against a fixture library of real fiscal documents (anonymized). Each fixture has a known expected output — these are regression tests for extraction accuracy.

**No mocking required**: There is no infrastructure to mock. The only external call is Gemini in the image branch; inject a `FakeExtractor` via the extractor interface for tests that do not need a live Gemini call.

**Coverage requirement**: All type validators (CNPJ, CPF, moeda_brl, data, etc.) must have 100% branch coverage — these are correctness-critical.
