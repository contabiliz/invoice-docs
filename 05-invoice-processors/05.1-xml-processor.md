# 05.1 XML Processor

## 05.1.1 Overview

The XML processor handles NF-e XML files (Nota Fiscal Eletrônica) issued under the SEFAZ modelo 55 schema. It validates the document against the official XSD schema, then extracts fiscal fields via XPath. No AI is involved. The SEFAZ schema is fixed by Brazilian federal law — XPath paths do not change unless SEFAZ publishes a new schema version, and even then the changes are versioned and backwards-compatible.

---

## 05.1.2 Architecture Decision Records

### ADR-001 — lxml over stdlib ElementTree

**Decision:** Use `lxml` for all XML parsing and XSD validation. Do not use Python's stdlib `xml.etree.ElementTree`.

**Reasons:**
- `ElementTree` does not support XSD schema validation. `lxml` supports it natively via `XMLSchema.validate()`.
- `lxml` exposes all required security flags as parser constructor arguments. `ElementTree` does not.
- `lxml` supports namespace-aware XPath (`xpath()` with `namespaces=` parameter). `ElementTree`'s XPath support is limited.

**Consequences:** `lxml` is a C extension. It must be present in the container image. The wheel is architecture-dependent — build for the target architecture (linux/amd64 or linux/arm64) in CI.

---

### ADR-002 — XPath over Regex or AI for NF-e XML

**Decision:** Extract all fields via XPath paths defined against the SEFAZ XSD schema. Do not use regex against the raw XML string. Do not pass XML content to the Gemini API.

**Reasons:**
- The SEFAZ NF-e schema (`nfe_v4.00.xsd`) is legally mandated. Every valid NF-e XML has exactly the same structure. XPath paths are deterministic.
- Regex against raw XML is fragile: it breaks on attribute order changes, whitespace differences, and namespace prefix variations.
- Sending XML content to Gemini is expensive, slow, subject to rate limits, and nondeterministic — all unnecessary when the data is already structured.

**Consequences:** A XPath field mapping table must be maintained per schema version. When SEFAZ publishes a new schema version (currently v4.00), the mapping must be updated and a new XSD file added. The processor must select the correct XSD based on the `versao` attribute in the root element.

---

### ADR-003 — Terminal Failure on XSD Validation Error

**Decision:** If the document fails XSD validation, return a terminal failure result immediately. Do not retry. Do not route to the DLQ.

**Reasons:**
- An XSD-invalid NF-e XML cannot be fixed by retrying. The file is either corrupt, truncated, or not a valid NF-e. The same parse will fail on every attempt.
- Retrying consumes queue capacity and delays other documents.
- The DLQ is for human review of transient failures. A structurally invalid document is not a transient failure.

**Consequences:** The `ExtractionResult` must carry a terminal failure flag that `invoice-pipeline` checks before applying retry logic. If `result.is_terminal_failure` is `True`, the worker marks the document `failed` and does not raise a retryable exception.

---

### ADR-004 — Security Flags Are Required, Not Optional

**Decision:** All four lxml security flags must be set on every parser instantiation. There are no exceptions.

**Reasons (finding C-10):**
- `resolve_entities=False`: Disables entity expansion. Without this, an `<!ENTITY xxe SYSTEM "file:///etc/passwd">` reference in the XML is expanded by the parser, leaking filesystem content or making internal network requests.
- `no_network=True`: Disables external resource fetching. Prevents the parser from making outbound HTTP/FTP requests to attacker-controlled servers via `SYSTEM` or `PUBLIC` identifiers.
- `huge_tree=False`: Prevents deeply nested or extremely large XML documents from exhausting stack space or memory. The default `huge_tree=True` in some lxml versions removes this protection.
- `load_dtd=False`: Disables DTD loading entirely. The NF-e schema does not use DTDs. Any DTD in the input is an attacker artifact.

**Consequences:** The parser is initialized once with these flags. No code path may construct an `lxml.etree.XMLParser()` without all four flags.

## 05.1.3 Processing Pipeline

```
bytes
  │
  ▼
Magic byte check
  │ not b'<?xml' → terminal failure (wrong file type)
  ▼
lxml.etree.fromstring(bytes, parser=secure_parser)
  │ parse error → terminal failure (malformed XML)
  ▼
Read versao attribute from root element
  │ unknown version → terminal failure
  ▼
XMLSchema.validate(tree)
  │ invalid → terminal failure (XSD validation failure)
  ▼
XPath extraction
  │ for each field in FIELD_MAP
  ▼
Type normalization (CNPJ, CPF, BRL, dates)
  ▼
ExtractionResult (success)
```

---

## 05.1.4 Parser Initialization

```python
from lxml import etree

SECURE_PARSER = etree.XMLParser(
    resolve_entities=False,
    no_network=True,
    huge_tree=False,
    load_dtd=False,
)
```

This parser instance is created once at module load. It is stateless and safe to reuse across invocations.

## 05.1.5 Supported Schema Versions

| versao attribute | XSD file |
|---|---|
| `4.00` | `schemas/nfe_v4.00.xsd` |

The `versao` attribute is read from the root `<nfeProc>` or `<NFe>` element before validation. If the version is not in the supported table, the document is terminal-failed with reason `"unsupported NF-e schema version: {versao}"`.

## 05.1.6 XPath Field Mapping

The NF-e XML uses the namespace `http://www.portalfiscal.inf.br/nfe`. All XPath queries must include the namespace binding.

```python
NS = {"nfe": "http://www.portalfiscal.inf.br/nfe"}
```

| Field | XPath |
|---|---|
| `chave_acesso` | `//nfe:infProt/nfe:chNFe` |
| `cnpj_emitente` | `//nfe:emit/nfe:CNPJ` |
| `nome_emitente` | `//nfe:emit/nfe:xNome` |
| `cnpj_destinatario` | `//nfe:dest/nfe:CNPJ` |
| `cpf_destinatario` | `//nfe:dest/nfe:CPF` |
| `nome_destinatario` | `//nfe:dest/nfe:xNome` |
| `data_emissao` | `//nfe:ide/nfe:dhEmi` |
| `valor_total_nota` | `//nfe:total/nfe:ICMSTot/nfe:vNF` |
| `numero_nota` | `//nfe:ide/nfe:nNF` |
| `serie` | `//nfe:ide/nfe:serie` |

**Item-level extraction (line items):**

Each `<det>` element represents one product/service line:

| Field | XPath (relative to `//nfe:det`) |
|---|---|
| `numero_item` | `@nItem` |
| `codigo_produto` | `nfe:prod/nfe:cProd` |
| `descricao` | `nfe:prod/nfe:xProd` |
| `quantidade` | `nfe:prod/nfe:qCom` |
| `unidade` | `nfe:prod/nfe:uCom` |
| `valor_unitario` | `nfe:prod/nfe:vUnCom` |
| `valor_total_item` | `nfe:prod/nfe:vProd` |
| `ncm` | `nfe:prod/nfe:NCM` |
| `cfop` | `nfe:prod/nfe:CFOP` |

## 05.1.7 Terminal Failure Conditions

The following conditions result in `ExtractionResult.is_terminal_failure = True`. None are retried.

| Condition | Reason string |
|---|---|
| Bytes do not start with `<?xml` | `"magic byte mismatch: not an XML file"` |
| lxml parse error | `"malformed XML: {lxml error message}"` |
| `versao` attribute missing or unrecognized | `"unsupported NF-e schema version: {value}"` |
| XSD validation failure | `"XSD validation failed: {first error message}"` |

All other exceptions (unexpected AttributeError, etc.) are treated as retryable bugs and raised to trigger Celery's retry mechanism.

## 05.1.9 What Not To Do

**Do not use `ElementTree` from stdlib.**
It does not support XSD validation and cannot set the required security flags. Using it makes the processor vulnerable to XXE and XML bomb attacks.

**Do not construct a new parser per invocation.**
Parser construction has overhead. `SECURE_PARSER` is a module-level constant.

**Do not parse the `versao` attribute after calling `validate()`.**
Read the version first — if the version is unsupported, you should not attempt validation against a mismatched schema, which would produce misleading error messages.

**Do not catch `etree.XMLSyntaxError` as a retryable error.**
A malformed document will always fail. Raise a terminal failure, not a retryable exception.

**Do not silently ignore missing XPath fields.**
If a mandatory field (e.g., `chave_acesso`) is absent in an XSD-valid document, it is an extraction bug — log it and raise, do not return a partial result.

**Do not pass the XML content to Gemini.**
XML with a fixed schema does not require AI extraction. Doing so would be expensive, slow, and nondeterministic for data that is already perfectly structured.

**Do not store the raw XML in `extracted_data`.**
`extracted_data` in the database stores the normalized `ExtractionResult` fields only. Raw XML is already persisted in Supabase Storage.
