# 05.2 PDF Processor

## 05.2.1 Overview

The PDF processor handles DANFE (Documento Auxiliar da Nota Fiscal Eletrônica) PDF files. Unlike the XML processor, it has no fixed machine-readable schema — it must reason spatially about a visual document. The implementation uses two complementary libraries: **pdfplumber** for text and table extraction, and **PyMuPDF** for geometric analysis of the vector drawing layer. Together they enable cell-based field extraction that is robust to font and layout variations.

If the extracted text falls below a confidence threshold (too sparse to be a digital PDF), the document is classified as a scanned PDF and routed to the image branch for Gemini-based extraction.

---

## 05.2.2 Architecture Decision Records

### ADR-001 — Dual-Library Approach: pdfplumber + PyMuPDF

**Decision:** Use pdfplumber for word extraction and table detection, and PyMuPDF (`fitz`) for geometric edge and vertex extraction. Neither library is sufficient alone.

**Reasons:**
- pdfplumber reliably extracts text bounding boxes and detects table structures from text positioning. However, its cell boundary detection relies on text alignment heuristics that fail when cells are empty or when values are not adjacent to their labels in the reading order.
- PyMuPDF exposes the vector drawing layer of the PDF (lines, rectangles, quads). DANFE PDFs are printed with drawn grid lines. Computing intersection vertices of these lines gives the exact cell boundaries regardless of cell content.
- Combining both: use pdfplumber words for text, use PyMuPDF vertices for cell boundary detection. This produces reliable cell-bounded extraction even for empty cells and for values that are far from their key label.

**Consequences:** Both libraries must be installed in `worker-pdf`. The container image is larger than a text-only approach. The dual adapter adds complexity — `PdfHandle` composites both adapters and merges their output into a unified `Document` model.

---

### ADR-002 — Profile-Based Architecture for Document Layouts

**Decision:** Document layouts are defined as `FiscalProfile` subclasses, not hardcoded in the extraction logic. The extraction engine is layout-agnostic.

**Reasons:**
- DANFE NF-e modelo 55 is the primary target, but the system must accommodate NF-e modelo 65 (NFC-e) and NFS-e (service invoices) in future without rewriting extraction logic.
- Layout differences (section anchor phrases, field search zones, XPath equivalents as label/alias sets) are configuration, not code.
- Profile-specific field overrides (constraining a field search to a specific section) prevent false positives from label repetition across sections.

**Consequences:** Each new document layout requires a new `FiscalProfile` subclass with: section anchor phrases, field overrides, and a `table_section_id`. The extraction engine (`ExtractionService`) remains unchanged.

---

### ADR-003 — Confidence Threshold for Text vs. Image Routing (H-02)

**Decision:** If the number of words extracted by pdfplumber is below `MIN_WORDS_THRESHOLD = 30`, classify the document as a scanned PDF and return a routing signal to `invoice-pipeline` to re-enqueue as an image task.

**Reasons:**
- Scanned PDFs are PDF containers holding a raster image of the original document. pdfplumber extracts near-zero words from them. Processing them through the text extraction pipeline produces empty or incorrect output.
- 30 words is a conservative threshold: a minimal DANFE contains dozens of field labels and values. If fewer than 30 words are extracted, the document is almost certainly a raster scan.

**Calibration note:** The threshold was calibrated against a fixture corpus of real DANFE PDFs. It should be re-evaluated if new document layouts are added. The threshold is a named constant in `invoice_processors.pdf.adapters.pdfplumber_adapter`.

**Consequences:** `ExtractionResult` must carry a `routing_override` field that `invoice-pipeline` checks. If `routing_override == "image"`, the worker does not write a completed result — it publishes a new Celery task to `queue.img` for the same `document_id`. The document status does not change during rerouting.

---

### ADR-004 — Scanned PDF Double-Processing Prevention (H-07)

**Decision:** When a PDF is rerouted to the image branch, the `document_id` is passed in the image task payload with a flag `source="pdf_fallback"`. The image worker writes the completed result to the same `document_id` record. The PDF worker does not write any result to the database before rerouting.

**Reasons:**
- Without explicit tracking, a Celery retry of the PDF task (after the rerouting publish) could re-process the PDF and create a second completed record or overwrite the image branch's result.
- If the PDF worker writes an intermediate "routing in progress" status, a crash between the write and the Redis publish leaves the document stuck in a non-retryable state.

**Consequences:** The rerouting flow is: PDF worker detects scan → publishes image task (with `document_id` + `source="pdf_fallback"`) → returns without raising, without writing to DB. Celery marks the PDF task as completed (no retry). The image worker processes and writes the final result.

---

### ADR-005 — pdfplumber as a Context Manager (H-16)

**Decision:** `pdfplumber.open()` must always be used as a context manager (`with pdfplumber.open(...) as pdf`). It must never be opened and closed manually.

**Reasons:**
- pdfplumber holds open file handles to the PDF data. Under load (hundreds of concurrent PDF tasks), manual open/close without exception handling leaks file descriptors and eventually exhausts the OS limit (default 1024 per process).
- The context manager guarantees `close()` is called even if an exception occurs mid-extraction.

**Consequences:** `PdfPlumberAdapter` is a context manager itself. All callers must use `with PdfPlumberAdapter(...) as adapter`.

---

### ADR-006 — pdf2image Must Write to tmpfs, Not Memory (H-17)

**Decision:** When converting PDF pages to images via `pdf2image.convert_from_path()`, always specify `output_folder` pointing to a tmpfs path (e.g., `/tmp`). Never use the default in-memory mode.

**Reasons:**
- In-memory conversion loads all page images as PIL objects simultaneously. A multi-page DANFE (8-12 pages) at print resolution (300 DPI) produces 80–120 MB of image data in memory per document.
- Under concurrent PDF tasks, this causes OOM kills on worker containers with 512 MB–1 GB memory.
- tmpfs writes are fast (memory-backed on Linux) and bounded by disk capacity, not the process heap.

**Consequences:** Worker containers must have a writable `/tmp`. The output folder must be cleaned up after processing. Use `tempfile.mkdtemp()` to create a unique directory per task and `shutil.rmtree()` in a `finally` block.

## 05.2.3 Processing Pipeline

```
bytes
  │
  ▼
Magic byte check (PDF magic: %PDF)
  │ mismatch → terminal failure
  ▼
Write bytes to NamedTemporaryFile (tmpfs)
  │
  ▼
PdfHandle.parse()  ←── pdfplumber: words + bounding boxes
  │                ←── PyMuPDF:    edges → vertices
  │
  ▼
DocumentStatus check
  │ total_words < 30 → return ExtractionResult(routing_override="image")
  ▼
FiscalProfile.extract(page)  ←── section slicing by anchor phrases
  │                                (HEADER, DESTINATARIO_REMETENTE,
  │                                 CALCULO_IMPOSTO, etc.)
  ▼
ExtractionService._extract_fields(fields, page, sections)
  │  for each FieldSpec:
  │    1. KeyCandidateFinder → list[KeyCandidate]
  │    2. ValueCandidateFinder → list[ValueCandidate] per zone
  │    3. TypeValidator → TypeValidationResult
  │    4. FieldScorer → ScoredCandidate
  │    5. ConflictResolver → best ScoredCandidate
  │
  ▼
ExtractionService._extract_tables(pdf, section, profile)
  │  TableItemsExtractor: try strategies in priority order
  │    → score each via header/consistency/fill/row_count
  │    → pick best strategy result
  │    → TableAdapter.parse_table() → list[dict]
  │
  ▼
ExtractionResult (success)
```

## 05.2.4 Geometric Cell Extraction

DANFE PDFs are typeset with drawn grid lines (rectangles and lines in the vector layer). Each field occupies a labeled cell. The cell boundary is defined by four vertices at the corners of the enclosing rectangle.

### Vertex Computation

1. PyMuPDF's `page.get_drawings()` returns all vector objects (lines, quads, rectangles).
2. Each object is decomposed into horizontal (`"h"`) and vertical (`"v"`) edges based on orientation threshold (2.0 pt default).
3. Full-page-spanning edges are discarded (ratio > 0.9 of page width/height) — they are border decorations, not cell boundaries.
4. Edges are deduplicated via rounded coordinate key.
5. Vertex intersection: for each horizontal edge, binary search finds candidate vertical edges by x-coordinate. Each (h, v) pair is checked for intersection within a spatial tolerance (1.0 pt). Intersections become `Vertex(x, y)` points.

### Cell Boundary Detection (within_cell_bounds zone)

Given a matched key label `WordBox`, find the enclosing cell:

1. **Top-left corner (v1)**: Nearest vertex above-left of the key (within 5 pt tolerance).
2. **Top-right corner (v2)**: Rightmost vertex on the same horizontal line as v1 that extends past the key's right edge.
3. **Bottom-right corner (v3)**: Bottommost vertex on the same vertical line as v2 that extends below the key's bottom.
4. **Bottom-left corner (v4)**: Verify existence at `(v1.x, v3.y)`. If missing, the cell boundary is incomplete — fall back to other zones.
5. If all four corners found: cell bounds are `(v1.x, v1.y, v2.x, v3.y)`.

Words within cell bounds, excluding the key's own row, are the value candidates.

## 05.2.5 Field Extraction Pipeline

### Key Candidate Finding

Three-tier search strategy (in order):

| Tier | Method | Confidence | Source |
|---|---|---|---|
| Primary | N-gram phrase match of `field.labels` | 1.00 | Exact label text |
| Secondary | N-gram phrase match of `field.aliases` | 0.93 | Common abbreviations/variants |
| Fallback | Line-based search | 0.85 | Not yet implemented |

N-gram search validates spatial coherence: matched tokens must be in reading order, within 3.0 pt vertical drift, and consecutive words must not have more than 20 pt horizontal gap. Normalization is accent-insensitive and uppercase.

### Value Candidate Zones

Each `FieldSpec` declares which zones to search (in order):

| Zone | Description |
|---|---|
| `within_cell_bounds` | Words inside the cell defined by surrounding vertices, excluding key row |
| `right_of_key` | Words on the same row as the key, to the right, grouped by horizontal gap (15 pt) |
| `same_row_after_colon` | Like `right_of_key` but skips a leading `:` or `;` separator |
| `below_key` | First row of words below the key, horizontally aligned with it |

### Scoring

Each (key, value) pair receives a composite score:

```
final = w_key * key_score + w_dist * dist_score + w_type * type_score + w_cross * cross_score
```

- **key_score**: Key candidate confidence (0.85–1.00)
- **dist_score**: Inverse of Manhattan gap between key and value (0.0 at 250 pt gap, 1.0 for overlap)
- **type_score**: 1.0 if type validation passed, 0.0 if failed
- **cross_score**: Cross-field consistency (placeholder = 1.0, not yet implemented)

Field-specific weights are declared in `_FIELD_WEIGHTS`. Fields where type validation is critical (CNPJ, chave_acesso) have higher `w_type`. Fields in fixed positions (header section) have higher `w_dist`.

### Type Validators

| Type key | Validates | Normalizes to |
|---|---|---|
| `cnpj` | 14-digit check digit algorithm | `XX.XXX.XXX/XXXX-XX` |
| `cpf` | 11-digit check digit algorithm | 11-digit string |
| `cpf_ou_cnpj` | Delegates by digit count | Same as above |
| `texto_numerico_44` | Exactly 44 digits | Digit string |
| `moeda_brl` | Brazilian decimal format (`.` thousands, `,` decimal) | Float string |
| `data` | DD/MM/YYYY, YYYY-MM-DD, and variants | `YYYY-MM-DD` |
| `cidade_uf` | City name + valid UF code | `CIDADE/UF` |
| `texto` | Non-empty string | Whitespace normalized |

### Conflict Resolution

If multiple (key, value) candidates exist for a field, the one with the highest `(score_final, type_score)` tuple is selected. Candidates below `field.min_score` are discarded. If no candidate meets the threshold, `FieldOutput` carries an error reason.

## 05.2.6 Table Extraction

The product/service items table in DANFE PDFs is extracted via pdfplumber's table detection, applied only to the `DADOS_PRODUTOS_SERVICOS` section.

### Strategy Selection

Four pdfplumber strategies are tried in priority order:

| Priority | Strategy name | Approach |
|---|---|---|
| 0 | `lines_strict` | Detect table from drawn lines only, strict snap |
| 1 | `lines` | Drawn lines with looser snap/join tolerances |
| 2 | `lines_text` | Drawn lines augmented by text alignment |
| 3 | `text` | Text positioning only (no line detection) |

Each strategy result is scored on four dimensions:

| Dimension | Weight | Description |
|---|---|---|
| Header quality | 0.30 | Column count valid (3–25), fill ratio, coherent cell sizes |
| Row consistency | 0.30 | Percentage of rows matching header column count |
| Fill rate | 0.25 | Non-empty cells / total cells |
| Row count | 0.15 | Penalizes 0 rows; 1 row gets partial credit; 2+ rows full |

The strategy with the highest composite score is used. If composite < 0.60, `low_confidence = True` is set on the result, which `invoice-pipeline` logs as a warning.

### Double-Line Header Normalization

DANFE tables frequently use two-row headers where the first row contains a category label spanning multiple columns and the second row contains sub-column names. Example:

```
| VALOR  |        |        | ALÍQUOTA |
| ICMS   | IPI    | IBS    | ICMS %   |
```

The table adapter detects spanning cells (second row contains `None` markers) and merges them:
→ `["VALOR ICMS", "VALOR IPI", "VALOR IBS", "ALÍQUOTA ICMS %"]`

### Known Gap: Table Normalization

The current implementation returns raw parsed rows as `list[dict[str, str | None]]`. Column names come directly from the PDF header row — they are not yet normalized to canonical field names.

**What is missing:**
- Mapping raw column names (e.g., `"DESCRIÇÃO DO PRODUTO / SERVIÇO"`, `"DESCRICAO"`) to canonical keys (e.g., `"descricao"`)
- Value normalization for table cells (CFOP as string, quantities as Decimal, monetary values in BRL format)
- Handling layout variants where column names differ between document subtypes

This normalization must be added before table data is written to `extracted_data`. The canonical output schema is defined in `invoice-models`.

## 05.2.7 Integration with invoice-models

The current `invoice-workers` implementation uses its own internal schema (`schemas/`). Before integration into the `invoice-processors` package, the internal types must be replaced with types from `invoice-models`.

| Internal type | invoice-models equivalent |
|---|---|
| `FieldOutput` | `invoice_models.extraction.FieldOutput` |
| `ExtractionResult` | `invoice_models.extraction.PdfExtractionResult` |
| `NfeLineItem` (table row) | `invoice_models.extraction.NfeLineItem` |

The extraction engine's internal types (`WordBox`, `Edge`, `Vertex`, `ScoredCandidate`, etc.) remain internal to `invoice-processors` — they are not part of the public contract.

## 05.2.8 What Not To Do

**Do not open pdfplumber outside a context manager.**
File handle leaks under load exhaust OS file descriptor limits. Always use `with pdfplumber.open(...) as pdf`.

**Do not convert PDF pages to images in memory.**
`pdf2image.convert_from_path()` without `output_folder` loads all pages as PIL objects simultaneously. Multi-page documents at print resolution cause OOM kills. Always specify `output_folder` pointing to tmpfs.

**Do not write any database record before rerouting to the image branch.**
The PDF worker must publish the image task and return cleanly. Writing an intermediate status creates a gap where a Celery retry re-enters the PDF branch after the image task is already in flight.

**Do not hardcode field labels in the extraction logic.**
Label strings belong in `FieldSpec.labels` and `FieldSpec.aliases`, not in the extraction pipeline code. The engine is layout-agnostic — it receives a profile and specs.

**Do not ignore low_confidence results from table extraction.**
If `TableScore.low_confidence` is True, log a structured warning with the document_id, strategy used, and composite score. This is signal for calibration, not an error to suppress.

**Do not use the same `min_score` threshold for all fields.**
Fields with high-cardinality values (CNPJ, chave_acesso) need a higher `min_score` because a false positive is worse than a missed extraction. Fields with low-cardinality values (series number, single-digit) can have a lower threshold.

**Do not rely on pdfplumber table detection alone for cell-bound values.**
pdfplumber's cell detection works well for dense tables but misidentifies cells when the PDF has decorative lines or non-uniform cell sizes. The vertex-based approach (`within_cell_bounds` zone) is more reliable for labeled field cells outside the product table.

**Do not add the raw extraction scores or internal debug data to `extracted_data`.**
`extracted_data` in the database must contain only the normalized business values. Scoring data, candidate lists, and method metadata belong in structured logs, not the database record.
