# 04.1 invoice-pipeline — Technical Specification

## 04.1.1 Overview

`invoice-pipeline` is the Celery application. It contains the task definitions for all three processing branches (XML, PDF, image), the DLQ worker, and the Celery application configuration. It is the orchestration layer: it downloads files from storage, calls the appropriate processor from `invoice-processors`, persists results to the database, and manages the full task lifecycle including retries and failure handling.

It contains no processing logic. All parsing, validation, and extraction belongs in `invoice-processors`.

**Package:** `invoice-pipeline`
**Runtime:** Celery 5.4+ with Python 3.12
**Deployment:** Railway or AWS ECS — three separate worker services plus one DLQ worker service

---

## 04.1.2 Architecture Decision Records

### ADR-001 — acks_late=True and task_reject_on_worker_lost=True

**Decision:** All Celery tasks run with `acks_late=True` and `task_reject_on_worker_lost=True` set globally.

**Context:** By default, Celery acknowledges a task (removes it from the queue) the moment a worker receives it. If the worker process is killed during execution — OOM kill, spot instance interruption, ECS task replacement — the task disappears silently with no retry and no DLQ entry. The document is stuck in `processing` status with no path to resolution.

**Reasons:**
- `acks_late=True` delays acknowledgement until the task function returns successfully. If the worker dies mid-execution, the task is returned to the queue and redelivered to another worker.
- `task_reject_on_worker_lost=True` ensures that when a worker process is killed unexpectedly (rather than gracefully), the task is rejected back to the queue rather than acknowledged.
- Together these flags implement at-least-once delivery. Tasks may run more than once — all task implementations must be idempotent.

**Consequences:** Tasks must be idempotent. Database writes must use `INSERT ... ON CONFLICT DO UPDATE` (upsert), not plain `INSERT`. A task that runs twice must produce the same final state as a task that runs once.

---

### ADR-002 — Three Separate Queues with Separate Pool Backends

**Decision:** Each processing branch runs on its own Celery queue (`queue.xml`, `queue.pdf`, `queue.img`) with its own worker container and Celery pool backend.

**Context:** XML, PDF, and image tasks have fundamentally different resource profiles:

| Branch | Bottleneck | Optimal pool |
|---|---|---|
| Image | I/O-bound — waits on Gemini HTTP response | `gevent` |
| XML | CPU-light, fast — lxml parsing is quick | `gevent` |
| PDF | CPU-bound — pdfplumber + pdf2image are compute-intensive | `prefork` |

Running all three in a single fleet with a single pool backend means choosing one backend that is suboptimal for at least two branches. A PDF surge on a `gevent` pool blocks all greenlets on CPU work, starving the image queue. A `prefork` pool on image workers wastes all processes blocking idle on Gemini HTTP.

**Reasons:**
- Separate containers allow independent autoscaling per queue depth.
- Separate pool backends allow each branch to be optimally configured.
- Separate queues allow the Consumer to route tasks precisely without worker competition.

**Consequences:** Three worker container definitions (or ECS task definitions / Railway services). The `invoice-pipeline` package is the same codebase in all three — the queue and pool are set via environment variables at container launch.

---

### ADR-003 — result_backend=None

**Decision:** The Celery result backend is disabled.

**Context:** By default, Celery stores task results in the broker (Redis) and allows callers to poll for them using `AsyncResult`. This system does not use that mechanism — all status and output is written to PostgreSQL by the task itself.

**Reasons:**
- The result backend duplicates state that already exists in PostgreSQL with higher durability and queryability.
- Results stored in Redis consume memory and require a TTL configuration to prevent unbounded growth.
- Polling via `AsyncResult` from the API is an anti-pattern here — the API reads from PostgreSQL, not from the result backend.

**Consequences:** `task.delay().get()` cannot be used. All result access goes through the database. This is intentional.

---

### ADR-004 — JSON Serializer Only

**Decision:** `task_serializer="json"`, `result_serializer="json"`, `accept_content=["json"]` are set globally on the Celery app. Pickle is explicitly disabled.

**Context:** Celery's default serializer is pickle. Deserializing an arbitrary pickle payload from Redis is equivalent to arbitrary code execution. If an attacker gains write access to the Redis broker, they can execute any code on every worker in the fleet.

**Reasons:**
- JSON serialization eliminates the deserialization attack vector.
- `accept_content=["json"]` causes workers to reject any message not serialized as JSON — including crafted pickle payloads.
- All task payloads are defined as Pydantic models in `invoice-models`, which serialize cleanly to JSON.

**Consequences:** Task arguments must be JSON-serializable. No Python objects, no datetimes without ISO conversion, no bytes without base64. Task payloads only contain strings and primitives — file content is never passed through the queue.

---

### ADR-005 — Gemini Rate Limiter via Redis Token Bucket

**Decision:** A shared token bucket rate limiter, backed by Redis, is enforced before every Gemini API call across all image workers.

**Context:** Gemini API has a rate limit (requests per minute). Without a client-side limiter, multiple workers compete to call Gemini simultaneously, trigger 429 responses, retry, collide again, and fill the DLQ. Scaling workers without a limiter reduces effective throughput rather than increasing it.

**Reasons:**
- A Redis token bucket is shared across all worker instances — it reflects the true global call rate, not a per-process estimate.
- Implemented as a Lua script on Redis to guarantee atomicity: token check and token decrement happen in one operation with no race condition.
- Workers that cannot acquire a token block briefly and retry locally, rather than submitting a Celery retry (which would requeue the task and waste a queue slot).

**Consequences:** The rate limiter adds one Redis round-trip before each Gemini call. At ~1ms, this is negligible compared to Gemini's typical response time of 1–5 seconds. The Gemini client is wrapped in a `RateLimitedExtractor` class inside `invoice-processors` — the limiter logic lives in `invoice-pipeline` and is injected at task invocation time.

## 04.1.3 Celery Application Configuration

```python
# invoice-pipeline/celery_app.py

app = Celery("invoice")

app.conf.update(
    # Serialization — ADR-004
    task_serializer="json",
    result_serializer="json",
    accept_content=["json"],

    # Delivery guarantees — ADR-001
    task_acks_late=True,
    task_reject_on_worker_lost=True,

    # Result backend — ADR-003
    result_backend=None,

    # Queue routing — ADR-002
    task_routes={
        "invoice.tasks.process_xml":   {"queue": "queue.xml"},
        "invoice.tasks.process_pdf":   {"queue": "queue.pdf"},
        "invoice.tasks.process_image": {"queue": "queue.img"},
        "invoice.tasks.handle_dlq":    {"queue": "queue.dlq"},
    },

    # Explicit task names — never rely on auto-naming from module paths
    # (package rename breaks all queued tasks silently)

    # Timezone
    timezone="UTC",
    enable_utc=True,
)
```

## 04.1.4 Queue and Worker Configuration

### Queue definitions

| Queue | Task | Pool | Concurrency | Branch profile |
|---|---|---|---|---|
| `queue.xml` | `process_xml` | `gevent` | 50 | Fast, I/O-light |
| `queue.pdf` | `process_pdf` | `prefork` | `nproc` | CPU-heavy (pdfplumber, pdf2image) |
| `queue.img` | `process_image` | `gevent` | 100 | I/O-bound (Gemini HTTP wait) |
| `queue.dlq` | `handle_dlq` | `prefork` | 4 | Low volume, DB writes only |

### Worker launch per container type

Each worker container type sets two environment variables that control which queue it listens to and which pool it uses:

```
WORKER_QUEUES=queue.xml
WORKER_POOL=gevent
WORKER_CONCURRENCY=50
```

The same Docker image handles all worker types. The queue, pool, and concurrency are deployment configuration, not code.

## 04.1.5 Task Structure

Every task follows the same three-step pattern. No exceptions.

```
1. download(storage_path)       → bytes
2. processor.process(bytes)     → ExtractionResult
3. db.write_result(document_id, result)
```

Status is updated at each boundary:

```
queued → processing    (first line of the task, before download)
processing → completed (after successful db.write_result)
processing → failed    (on terminal error, written directly — no retry)
```

### Status update on task entry

The first operation in every task must be an atomic status update from `queued` to `processing`. If the task runs twice due to `acks_late` redelivery, the second run sees `processing` and proceeds — the upsert on the final write ensures idempotency.

### Terminal vs retryable errors

| Error type | Action |
|---|---|
| Gemini 429 (rate limit) | Retry with exponential backoff |
| Gemini 5xx (server error) | Retry with exponential backoff |
| Network timeout (S3 download, DB write) | Retry with linear backoff |
| Gemini 400/401 (client error) | Terminal — write `failed`, no retry |
| Magic byte mismatch (`type_mismatch`) | Terminal — write `failed`, no retry |
| XML XSD validation failure | Terminal — write `failed`, no retry |
| Corrupt file (unparseable PDF, truncated image) | Terminal — write `failed`, no retry |
| Retries exhausted | Task moves to `queue.dlq` automatically |

Terminal errors write the `failed` status and `error_reason` to the database within the task itself. They do not raise an exception that triggers a retry — they call `self.update_state()` and return cleanly.

## 04.1.6 Retry Policy

### Default (all branches)

```python
@app.task(
    bind=True,
    name="invoice.tasks.process_xml",
    max_retries=4,
    default_retry_delay=30,      # seconds, base for exponential backoff
    autoretry_for=(NetworkError, TimeoutError),
    retry_backoff=True,
    retry_backoff_max=300,        # cap at 5 minutes
    retry_jitter=True,
)
```

### Gemini-specific (image branch only)

Gemini 429 responses use a separate retry configuration with a longer initial delay to allow the quota window to reset:

```python
autoretry_for=(GeminiRateLimitError,),
default_retry_delay=60,    # 1 minute base
retry_backoff=True,
retry_backoff_max=600,     # cap at 10 minutes
max_retries=5,
```

### Retry count summary

| Error | Max retries | Backoff |
|---|---|---|
| Gemini 429 | 5 | Exponential, 60s base, 10m cap |
| Gemini 5xx | 4 | Exponential, 30s base, 5m cap |
| Network / timeout | 3 | Linear, 30s |
| Terminal errors | 0 | None — immediate `failed` |

## 04.1.7 DLQ Worker

The DLQ worker is a separate Celery worker listening exclusively on `queue.dlq`. It handles tasks that have exhausted all retries.

### What the DLQ worker does

1. Receives the failed task payload (same schema as the original task)
2. Writes `status = "failed"` and `error_reason` to the document record
3. Increments `batch.failed_count` atomically
4. Logs the failure with full context for manual review
5. Does not delete the task — it remains in `queue.dlq` for inspection

### What the DLQ worker does not do

- Retry the task
- Modify the file in storage
- Notify the user directly (notification is triggered by the batch completion check)
- Auto-reprocess without manual intervention

### Batch completion check

After every write (whether `completed` or `failed`), the worker checks:

```sql
SELECT completed_count + failed_count = total_documents
FROM batches WHERE id = $1
```

If true, it updates `batch.status` to `completed`, `partial_failure`, or `failed` accordingly and emits a Supabase Realtime event so the frontend can stop polling.

| Condition | Batch status |
|---|---|
| All documents `completed` | `completed` |
| Some `completed`, some `failed` | `partial_failure` |
| All documents `failed` | `failed` |

## 04.1.8 Security Requirements

### Serializer (FW-001 / SEC-008 — Critical)

`accept_content=["json"]` must be set globally. Workers must reject any message that is not JSON. A crafted pickle payload in Redis is arbitrary code execution on the worker. This is not optional.

### Database credentials

Workers use a dedicated database user with `SELECT` on `documents` and `batches`, and `INSERT/UPDATE` on `documents`, `batches`, and `extracted_data`. They must not use the Supabase service role key.

Workers connect via the PgBouncer pooler endpoint (`DATABASE_URL`, port 6543, transaction pooling mode), not the direct connection URL. The direct URL (`DATABASE_DIRECT_URL`) is only for Alembic migrations.

### Redis credentials (SEC-013)

Workers connect to Redis with AUTH. The Redis instance is in a private network not accessible from outside the worker/API/Consumer subnet. TLS for Redis connections if using AWS ElastiCache.

### Container hardening (SEC-012)

- Non-root user (uid=1001)
- Read-only root filesystem
- `tmpfs` mounted at `/tmp` for pdf2image temporary output
- No capabilities beyond the default

### PII in logs (SEC-015)

Workers log `document_id`, `batch_id`, `doc_type`, `queue_name`, `retry_count`, and `error_type`. They never log file contents, extracted field values, CNPJ/CPF values, or `storage_path` beyond the first log line of a task.

## 04.1.9 Performance Requirements

### psycopg3 for database writes (FW-013)

Use `psycopg3` (sync, long-lived connection per worker process). One connection per process, reused across all task executions in that process. All database writes use upsert semantics:

```sql
INSERT INTO documents (id, status, ...) VALUES (...)
ON CONFLICT (id) DO UPDATE SET status = EXCLUDED.status, ...
```

Connect to PgBouncer in transaction pooling mode. Do not use session-level features (advisory locks, `SET LOCAL`, temporary tables) — they are not safe with transaction pooling.

### S3 downloads

Use `boto3` or the Supabase Storage SDK with a persistent session (not recreated per task). For large files, use streaming download to avoid loading the entire file into memory before processing begins.

### Batch completion counter atomicity

`batch.completed_count` and `batch.failed_count` are incremented using a single atomic SQL statement per task completion:

```sql
UPDATE batches
SET completed_count = completed_count + 1
WHERE id = $1
RETURNING completed_count + failed_count = total_documents AS is_complete
```

This avoids a separate SELECT/UPDATE cycle and eliminates the race condition where two workers simultaneously read the same count before incrementing.

### Celery pool backends (FW-005)

| Container | Pool | Why |
|---|---|---|
| `worker-img` | `gevent` | 100 greenlets, all idle during Gemini HTTP wait |
| `worker-xml` | `gevent` | 50 greenlets, fast I/O-light tasks |
| `worker-pdf` | `prefork` | `nproc` processes, CPU-bound rasterization |
| `worker-dlq` | `prefork` | 4 processes, low volume |

### Gemini rate limiter implementation

```python
RATE_LIMIT_SCRIPT = """
local key = KEYS[1]
local capacity = tonumber(ARGV[1])
local now = tonumber(ARGV[2])
local refill_rate = tonumber(ARGV[3])

local bucket = redis.call('HMGET', key, 'tokens', 'last_refill')
local tokens = tonumber(bucket[1]) or capacity
local last_refill = tonumber(bucket[2]) or now

local elapsed = now - last_refill
local refill = elapsed * refill_rate
tokens = math.min(capacity, tokens + refill)

if tokens >= 1 then
    tokens = tokens - 1
    redis.call('HMSET', key, 'tokens', tokens, 'last_refill', now)
    return 1
else
    return 0
end
"""
```

The script is loaded once and called via `EVALSHA`. Workers that cannot acquire a token sleep 1 second and retry locally — they do not requeue the Celery task.

## 04.1.10 Testing Requirements

### Must pass before any deployment

**T-CRIT-004 — Workers reject non-JSON messages**
Send a crafted pickle-serialized message directly to `queue.img` via Redis. Assert the worker raises a deserialization error and does not execute the payload. Assert the message is rejected, not acknowledged.

**T-CRIT-009 — acks_late redelivery is idempotent**
Run a task to partial completion (after status update to `processing`, before `db.write_result`), kill the worker process, restart. Assert the task is redelivered and completes successfully. Assert the final database state is identical to a clean run.

### High priority

**T-HIGH-004 — Retry exhaustion routes to DLQ**
Configure `max_retries=2`. Inject a retryable error on every attempt. After 2 retries, assert the task lands in `queue.dlq`. Assert the DLQ worker writes `failed` status and `error_reason` to the database.

**T-HIGH-005 — Batch completion counter atomicity**
Run 50 tasks concurrently against the same batch. Assert `completed_count + failed_count = 50` after all tasks finish. Run 50 times to surface any race condition.

**T-HIGH-011 — Terminal errors do not retry**
For each terminal error type (type_mismatch, XSD validation failure, Gemini 400, corrupt file): assert the task writes `failed` status in the same invocation, makes no attempt to retry, and does not reach the DLQ.

**T-MED-004 — Gemini rate limiter concurrency**
Start 10 image workers simultaneously. Each attempts to acquire a token from the same Redis bucket with capacity 5. Assert no more than 5 Gemini calls happen in the first window. Assert the remaining 5 workers wait and complete in the next window.

### Integration tests

Use `testcontainers-python` for both Redis and PostgreSQL. Use real Celery workers (not eager mode) for any test involving retries, DLQ routing, or `acks_late` behavior — eager mode bypasses these mechanisms entirely.

## 04.1.11 Implementation Notes

### Explicit task names

All tasks must declare an explicit `name` parameter:

```python
@app.task(bind=True, name="invoice.tasks.process_xml", ...)
def process_xml(self, ...):
```

Never rely on auto-generated names derived from the module path. If the package is renamed or the module is moved, auto-generated names change silently and all queued tasks become unroutable.

### Dependency management (FW-009)

`invoice-pipeline` is a `uv` workspace member. It declares `invoice-models` and `invoice-processors` as workspace dependencies. System dependencies (`libmagic1`, `poppler-utils`) are installed in the Docker image, not via `uv`.

### Docker base image (FW-015)

`python:3.12-slim-bookworm`. Not distroless — `poppler-utils` and `libmagic1` require a standard Debian package manager. Multi-stage build:

```dockerfile
FROM python:3.12-slim-bookworm AS builder
RUN apt-get install -y gcc libxml2-dev libxslt-dev
# compile C extensions (lxml, psycopg3)

FROM python:3.12-slim-bookworm AS runtime
RUN apt-get install -y --no-install-recommends \
    poppler-utils \
    libmagic1
COPY --from=builder /app /app
USER 1001
```

### Structured logging

Use `structlog` with JSON output. Bind `document_id`, `batch_id`, `doc_type`, `worker_type`, and `retry_count` to the log context at the start of each task using `structlog.contextvars.bind_contextvars()`. Every log line emitted during task execution automatically carries these fields.

### Secrets

| Variable | Used by |
|---|---|
| `DATABASE_URL` | All workers (PgBouncer pooler) |
| `REDIS_URL` | All workers (broker) |
| `CELERY_BROKER_URL` | All workers |
| `SUPABASE_STORAGE_URL` | All workers (file download) |
| `SUPABASE_SERVICE_ROLE_KEY` | All workers (storage access) |
| `GEMINI_API_KEY` | `worker-img` only — XML and PDF workers must not receive this |
| `GEMINI_RATE_LIMIT_RPM` | `worker-img` only |

The `GEMINI_API_KEY` must be scoped exclusively to the image worker service. XML and PDF workers have no reason to receive it. Least-privilege at the secret level, not just the role level.

## 04.1.12 What Not To Do

**Do not put processing logic in task functions.**
Tasks download, delegate, and persist. All parsing, validation, and extraction happens inside `invoice-processors`. A task function that contains lxml calls, Pillow transforms, or pdfplumber reads has violated the package boundary.

**Do not use pickle.**
`accept_content=["json"]` is not optional. A single misconfigured worker that accepts pickle is a full fleet compromise if Redis is reachable by an attacker.

**Do not disable `acks_late`.**
The default (acknowledge on receipt) silently drops documents when workers are killed. Fiscal documents cannot be silently lost — every document must either complete or fail explicitly.

**Do not use a single queue for all branches.**
Mixing branch types on one queue means a backlog of slow image tasks (waiting on Gemini) blocks fast XML tasks. Each branch gets its own queue.

**Do not use `prefork` for image workers.**
Each `prefork` process blocks idle waiting on Gemini HTTP. Use `gevent` — 100 concurrent greenlets on the same CPU, all progressing while others wait on I/O.

**Do not use `convert_from_bytes()` in the PDF worker (FW-007).**
It loads all rasterized pages into memory simultaneously. Use `convert_from_path(output_folder=tmp_dir)` to write pages to the `tmpfs` mount. A 50-page PDF at 300 DPI is ~600 MB in memory.

**Do not scale image workers without the rate limiter.**
More workers without the token bucket rate limiter produces more 429s, more retries, and more DLQ entries — not more throughput. The rate limiter must be in place before horizontal scaling.

**Do not use `result_backend` with Redis.**
All state lives in PostgreSQL. A result backend in Redis duplicates this state with no durability guarantee and unbounded memory consumption.

**Do not use session-level PostgreSQL features with PgBouncer transaction pooling.**
Advisory locks, `SET LOCAL`, and temporary tables are destroyed at transaction commit when using PgBouncer in transaction pooling mode. All operations within a task must complete within a single transaction or use explicit connection management.

**Do not ignore the `error_reason` field.**
Every terminal failure must write a human-readable `error_reason` to the database. "Unknown error" is not acceptable. The DLQ reviewer and the end user depend on this field to understand what went wrong and whether resubmission is possible.
