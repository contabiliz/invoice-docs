# 01.2 Package Structure

## 01.2.1 Overview

The backend is split into three packages with distinct responsibilities. The core principle is that processing logic has no knowledge of how it is invoked — Celery, HTTP, or direct call are all equivalent from the processor's perspective.

```
contabiliz/
├── invoice-models/       # Shared Pydantic schemas
├── invoice-processors/   # Pure processing logic
└── invoice-pipeline/     # Celery tasks and Consumer
```

---

## 01.2.2 invoice-models

Shared Pydantic schemas imported by all other packages. Defines the data contracts for task payloads, extraction results, and document status.

No business logic. No infrastructure dependencies.

---

## 01.2.3 invoice-processors

Pure Python processing logic for each document branch. No Celery, no S3 client, no database access. Takes bytes as input and returns structured data as output.

**Responsibilities:**
- XML: lxml XSD validation against the SEFAZ schema, XPath field extraction
- Image: Pillow preprocessing (resize, contrast enhancement), AI extraction via an injected `Extractor`
- PDF: pdfplumber text extraction, confidence scoring, routing to image branch if below threshold

**What it does not do:**
- Download files from storage
- Write to the database
- Publish messages to any queue
- Import or reference Celery

The Gemini client is injected into image processing as an `Extractor` dependency. The processor defines the interface; the pipeline provides the implementation. This keeps the processor testable without live API calls.

---

## 01.2.4 invoice-pipeline

Celery application containing all task definitions and the Consumer. Acts as the orchestration layer: downloads files, calls processors, persists results, and handles all retry and failure logic.

**Responsibilities:**
- Consumer: listens to Redis, reads document type from the database, publishes tasks to the correct queue
- Celery tasks: download file from storage → call the appropriate processor → write result to database
- Retry policy and DLQ routing
- Queue configuration and worker pool settings per branch

**What it does not do:**
- Contain parsing, validation, or extraction logic — that belongs in `invoice-processors`
- Define data schemas — those come from `invoice-models`

Each Celery task follows the same three-step structure:

```
download(storage_path) → processor.process(content) → db.write(document_id, result)
```

---

## 01.2.5 Dependency Direction

```
invoice-pipeline  →  invoice-processors  →  invoice-models
invoice-pipeline  →  invoice-models
invoice-processors  →  invoice-models
```

No package imports from a package above it in this chain. `invoice-models` imports nothing internal.

---

## 01.2.6 Testing Boundaries

| Package | Test approach |
|---|---|
| `invoice-models` | Schema validation unit tests |
| `invoice-processors` | Pure pytest with fixture files — no mocks of infrastructure |
| `invoice-pipeline` | Celery eager mode + testcontainers for Redis and PostgreSQL |
