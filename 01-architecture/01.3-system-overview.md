# 01.3 System Overview

## 01.3.1 Purpose

An event-driven pipeline for processing Brazilian SEFAZ fiscal documents. Users upload batches of documents (XML NF-e, PDF DANFE, or thermal paper images) and receive structured fiscal data extracted from each one. The system is multi-tenant, async by design, and built entirely in Python on the backend.

---

## 01.3.2 Components

| Component | Package / Service | Responsibility |
|---|---|---|
| **Frontend** | Next.js — Vercel | File upload, batch submission, status display |
| **API** | `invoice-api` — FastAPI | Presigned URLs, metadata creation, status queries |
| **Consumer** | `invoice-pipeline` — Python | Upload event listener, Celery task publisher |
| **XML Worker** | `invoice-pipeline` + `invoice-processors` | lxml XSD validation + XPath extraction |
| **PDF Worker** | `invoice-pipeline` + `invoice-processors` | pdfplumber extraction + pdf2image fallback |
| **Image Worker** | `invoice-pipeline` + `invoice-processors` | Pillow preprocessing + Gemini API extraction |
| **DLQ Worker** | `invoice-pipeline` | Failure handler for exhausted-retry tasks |
| **Redis** | AWS ElastiCache / Railway | Message broker — task queues + DLQ |
| **Supabase Storage** | Supabase | Raw file storage — presigned URL uploads |
| **Supabase PostgreSQL** | Supabase | System of record — all state and extracted data |
| **Gemini API** | Google (external) | Structured JSON extraction from preprocessed images |

## 01.3.3 End-to-End Data Flow

### Phase 1 — Batch Submission

```
Frontend                    API                      Supabase
   |                         |                           |
   |-- POST /batches/presign →|                           |
   |   [filename, mime_type,  |                           |
   |    file_size per doc]    |                           |
   |                         |-- validate mime_type       |
   |                         |-- normalize to xml/pdf/img |
   |                         |-- INSERT batch (DB)        |
   |                         |-- INSERT documents (DB)    |
   |                         |-- generate presigned URLs →|
   |←-- 202 + presigned_urls -|                           |
```

### Phase 2 — Direct Upload to Storage

```
Frontend                                       Supabase Storage
   |                                                  |
   |-- PUT presigned_url (file bytes) ───────────────→|
   |←-- 200 OK ───────────────────────────────────────|
   |                                                  |
   |-- POST /batches/{id}/confirm (object_key) ──→ API|
   |                         API: verify object exists |
   |                         API: UPDATE doc status    |
   |                              pending_upload       |
   |                              → upload_confirmed   |
   |                         API: PUBLISH to Redis     |
   |                              uploads.confirmed    |
```

### Phase 3 — Consumer Routes to Processing Queue

```
Redis                    Consumer                  PostgreSQL
   |                         |                         |
   |-- notification: ───────→|                         |
   |   { document_id,        |                         |
   |     batch_id }          |-- SELECT doc_type ─────→|
   |                         |←-- { doc_type,           |
   |                         |     s3_key }             |
   |                         |-- UPDATE status          |
   |                         |   upload_confirmed       |
   |                         |   → queued    ──────────→|
   |                         |-- INCREMENT              |
   |                         |   batch.queued_count ───→|
   |                         |-- PUBLISH Celery task   →| Redis
   |                         |   { document_id,         | queue.xml
   |                         |     s3_key, doc_type }   | queue.pdf
   |                         |                          | queue.img
```

### Phase 4 — Worker Processes Document

```
Redis (queue)        Worker                  Storage         PostgreSQL
   |                   |                        |                |
   |-- task ──────────→|                        |                |
   |                   |-- UPDATE status        |                |
   |                   |   queued → processing →|                |
   |                   |-- download(s3_key) ───→|                |
   |                   |←-- file bytes ─────────|                |
   |                   |                        |                |
   |                   |-- invoice-processors.process(bytes)     |
   |                   |   [XML: lxml + XPath]                   |
   |                   |   [PDF: pdfplumber or pdf2image]        |
   |                   |   [IMG: Pillow + Gemini API]            |
   |                   |                        |                |
   |                   |-- UPDATE document ─────────────────────→|
   |                   |   status = completed                    |
   |                   |   extracted_data = {...}                |
   |                   |   completed_at = now()                  |
   |                   |                        |                |
   |                   |-- UPDATE batch ─────────────────────────|
   |                   |   completed_count += 1                  |
   |                   |   RETURNING is_complete                 |
   |                   |                        |                |
   |                   |   if is_complete:                       |
   |                   |-- UPDATE batch.status ─────────────────→|
   |                   |   completed | partial_failure | failed  |
```

### Phase 4b — Worker Failure Path

```
Worker (on retryable error)        Redis               PostgreSQL
   |                                  |                    |
   |-- raise exception ──────────────→|                    |
   |   Celery retries with backoff     |                    |
   |   (up to max_retries)            |                    |
   |                                  |                    |
Worker (on terminal error)
   |-- UPDATE document ──────────────────────────────────→|
   |   status = failed                                     |
   |   error_reason = "..."                                |
   |   (no retry, no DLQ)                                  |
   |-- UPDATE batch.failed_count += 1 ───────────────────→|

Worker (retries exhausted → DLQ)
   |-- task routed to queue.dlq ─────→|
                                      |
DLQ Worker                            |                    |
   |←-- task ─────────────────────────|                    |
   |-- UPDATE document ──────────────────────────────────→|
   |   status = failed                                     |
   |   error_reason = "retries exhausted: ..."            |
   |-- UPDATE batch.failed_count += 1 ───────────────────→|
```

### Phase 5 — Frontend Polls Status

```
Frontend                   API                    PostgreSQL
   |                        |                         |
   |-- GET /batches/{id} ──→|                         |
   |                        |-- SELECT batch ─────────→|
   |                        |   (RLS: user_id filter)  |
   |←-- { status, counts } -|                         |
   |                        |                         |
   |-- GET /batches/{id}/   |                         |
   |   documents?status=    |                         |
   |   failed ─────────────→|                         |
   |                        |-- SELECT documents ─────→|
   |                        |   WHERE batch_id = $1    |
   |                        |   AND status = 'failed'  |
   |←-- [{ doc, error }] ───|                         |
```

## 01.3.4 State Machines

### Document Status

```
                    ┌─────────────────┐
                    │  pending_upload  │  ← created by API at presign time
                    └────────┬────────┘
                             │ API: upload confirmed by frontend
                             ▼
                    ┌─────────────────────┐
                    │  upload_confirmed   │
                    └────────┬────────────┘
                             │ Consumer: task published to queue
                             ▼
                    ┌────────────────┐
                    │    queued      │
                    └────────┬───────┘
                             │ Worker: task picked up
                             ▼
                    ┌────────────────┐
                    │  processing    │
                    └──────┬─────┬──┘
                           │     │
              success ─────┘     └───── terminal error
                           │           or retries exhausted
                           ▼                    ▼
                    ┌────────────┐     ┌──────────────┐
                    │ completed  │     │    failed    │
                    └────────────┘     └──────────────┘
```

**Terminal failures (no retry, no DLQ):**
- Magic byte mismatch between declared `doc_type` and actual file content
- XML XSD validation failure against SEFAZ schema
- Gemini 400/401 (client error)
- Corrupt or unparseable file

**Retryable failures (Celery retry → DLQ after exhaustion):**
- Gemini 429 (rate limit) — exponential backoff, 5 retries
- Gemini 5xx (server error) — exponential backoff, 4 retries
- Network timeout (S3 download, DB write) — linear backoff, 3 retries

### Batch Status

```
                ┌─────────────────┐
                │  pending_upload  │  ← created at presign time
                └────────┬────────┘
                         │ first document reaches queued
                         ▼
                ┌─────────────────┐
                │   processing    │
                └────────┬────────┘
                         │ completed_count + failed_count
                         │ = total_documents
                         ▼
           ┌─────────────┼──────────────┐
           │             │              │
     failed=0      0 < failed      completed=0
    completed=all   < total        failed=all
           │             │              │
           ▼             ▼              ▼
    ┌──────────┐  ┌──────────────┐  ┌────────┐
    │completed │  │partial_failure│  │ failed │
    └──────────┘  └──────────────┘  └────────┘
```

## 01.3.5 Package Dependencies

```
invoice-api
    └── invoice-models   (Pydantic schemas for request/response)

invoice-pipeline
    ├── invoice-models   (Pydantic schemas for task payloads)
    └── invoice-processors (pure processing logic per branch)

invoice-processors
    └── invoice-models   (Pydantic schemas for extraction results)
```

`invoice-models` is imported by everyone. No package imports from a package above it in this chain. `invoice-processors` has no knowledge of Celery, S3, or the database — it receives bytes and returns structured data.

## 01.3.6 Infrastructure Layout

```
Vercel
└── Next.js (frontend)

Railway / AWS ECS
├── invoice-api          (FastAPI — long-lived server)
├── worker-xml           (Celery, gevent pool, queue.xml)
├── worker-pdf           (Celery, prefork pool, queue.pdf)
├── worker-img           (Celery, gevent pool, queue.img)
└── worker-dlq           (Celery, prefork pool, queue.dlq)

AWS ElastiCache / Railway Redis
└── Redis                (broker: queue.xml, queue.pdf, queue.img, queue.dlq)
                         (Consumer channel: uploads.confirmed)

Supabase
├── PostgreSQL           (system of record + auth)
└── Storage              (raw file storage, presigned URL uploads)

External
└── Gemini API           (image extraction — image worker only)
```
