# 03.1 Consumer — Technical Specification

## 03.1.1 Overview

The Consumer is a Python service that bridges storage events and the processing queue. It listens for upload completion notifications on Redis, confirms the document record exists in the database, updates the document status, and publishes the Celery task to the correct processing queue.

It is the only component that publishes Celery tasks. It has no HTTP interface and performs no file processing.

**Package:** `invoice-pipeline`
**Language:** Python 3.12
**Deployment:** Railway or AWS ECS (same platform as workers)

---

## 03.1.2 Architecture Decision Records

### ADR-001 — Consumer Reads doc_type from the Database, Not from the File

**Decision:** The Consumer reads the normalized `doc_type` (`xml`, `pdf`, `img`) from the document record created by the API at presigned URL generation time. It does not download the file or inspect its contents.

**Context:** An alternative design would have the Consumer download the file and inspect magic bytes to determine the type. This was considered and rejected.

**Reasons:**
- The API already validates the declared MIME type and normalizes it before writing the record. Downloading the file in the Consumer would duplicate work that happens again in the worker (which validates actual content against declared type).
- File downloads in the Consumer add latency, introduce network failure modes, and create a second SSRF-adjacent surface.
- The Consumer's role is routing, not validation. Validation happens at the worker.

**Consequences:** The Consumer trusts the `doc_type` stored in the database. A wrong `doc_type` (from a mislabeled upload) causes the worker to write `failed` with reason `type_mismatch`. This is acceptable — the error is surfaced clearly and the document is not silently misrouted.

---

### ADR-002 — Upload Completion Notification via Redis, Published by the API

**Decision:** The upload completion event that triggers the Consumer is a Redis message published by the API after a successful presigned URL request — not a native Supabase Storage event or a direct S3 event notification.

**Context:** Supabase Storage does not support native object-creation event notifications (unlike AWS S3, which has S3 Event Notifications via SNS/SQS). A trigger mechanism must be designed explicitly.

**Three options were evaluated:**

| Option | Mechanism | Problem |
|---|---|---|
| A | S3 Event Notification → SNS → SQS → Redis | Requires switching to native AWS S3; Supabase Storage cannot do this |
| B | Frontend notifies API after upload; API publishes to Redis | The API already handles the upload flow — this is the natural extension |
| C | Supabase Realtime webhook on storage bucket | Supabase Realtime does not emit events on Storage object creation |

**Decision:** Option B. After the frontend completes an upload, it calls a confirmation endpoint on the API. The API verifies the object exists in storage, updates the document status from `pending_upload` to `upload_confirmed`, and publishes a lightweight notification to Redis. The Consumer picks this up and publishes the Celery task.

**Consequences:** There is one additional API call per document after upload. This is a small cost. The alternative (polling the database for `pending_upload` records) would require the Consumer to run on a timer and introduces processing delays.

---

### ADR-003 — Consumer Publishes Tasks, Not the API

**Decision:** The API does not publish Celery tasks directly. The Consumer is the sole publisher of Celery tasks to the processing queue.

**Context:** An alternative design would have the API publish the Celery task at the same time it generates the presigned URL, before the file is uploaded.

**Reasons:**
- If the API publishes a task before the file is uploaded, workers may pick up the task and attempt to download a file that does not yet exist in storage. This results in a failed task for a file that will eventually be uploaded — a preventable failure.
- The Consumer publishes only after the upload is confirmed. This guarantees the file is in storage when the worker picks up the task.
- Separating intake (API) from task publication (Consumer) keeps each component's responsibility narrow.

**Consequences:** There is a small delay between upload completion and task publication (the round trip through the confirmation endpoint and the Consumer). This is acceptable — the system is designed for async processing, not real-time response.

---

### ADR-004 — Consumer Lives in invoice-pipeline, Not invoice-processors

**Decision:** The Consumer is part of the `invoice-pipeline` package alongside Celery task definitions. It is not part of `invoice-processors`.

**Context:** The Consumer publishes Celery tasks, manages database status updates, and interacts with Redis — all infrastructure concerns. `invoice-processors` contains only pure processing logic with no infrastructure dependencies.

**Reasons:**
- The Consumer has no processing logic. It reads a type, constructs a task payload, and publishes.
- Placing it in `invoice-pipeline` keeps all orchestration (task definitions, task publishing, status transitions) in one package.

## 03.1.3 Functional Requirements

### What the Consumer does

1. **Listens** to a Redis channel for upload confirmation notifications published by the API.
2. **Reads** the document record from the database to retrieve `doc_type`, `storage_path`, and `document_id`.
3. **Validates** the record exists and is in `upload_confirmed` status. If not, discards the message and logs a warning.
4. **Updates** the document status from `upload_confirmed` to `queued`.
5. **Publishes** a Celery task to the correct queue based on `doc_type`:
   - `xml` → `queue.xml`
   - `pdf` → `queue.pdf`
   - `img` → `queue.img`
6. **Increments** `batch.queued_count` atomically in the database.
7. **Discards** the Redis notification message after successful task publication.

### What the Consumer does not do

- Download files from storage
- Inspect file contents or magic bytes
- Classify documents by filename or extension
- Process documents
- Write `failed` or `completed` status (that belongs to workers and the DLQ worker)
- Handle retries for processing failures (that belongs to Celery)
- Expose any HTTP interface

---

## 03.1.4 Message Contract

### Incoming notification (Redis channel: `uploads.confirmed`)

Published by the API after upload confirmation. The Consumer subscribes to this channel.

```json
{
  "document_id": "uuid",
  "batch_id": "uuid"
}
```

The message is intentionally minimal. The Consumer fetches all other context (doc_type, storage_path, user_id) from the database. This prevents stale data from being acted on if the notification is delayed.

### Outgoing Celery task payload (from invoice-models)

```json
{
  "document_id": "uuid",
  "batch_id": "uuid",
  "storage_path": "{user_id}/{batch_id}/{document_id}/filename.xml",
  "doc_type": "xml"
}
```

The task payload is defined in `invoice-models` as a Pydantic model and serialized to JSON. Workers deserialize using the same model. Schema drift between Consumer and worker is impossible — both import the same class.

---

## 03.1.5 Status Transitions

The Consumer is responsible for two status transitions:

```
upload_confirmed  →  queued        (on successful task publication)
```

If the database update succeeds but the Redis publish fails, the Consumer must not leave the document in `queued` status with no corresponding task in the queue. The update and publish must be treated as a unit:

1. Publish the Celery task to Redis
2. Only if the publish succeeds, update the status to `queued` and increment `batch.queued_count`

If the publish fails, the document remains in `upload_confirmed`. A retry of the notification (or a reconciliation job) can re-trigger the Consumer.

## 03.1.6 Security Requirements

### Database credentials

The Consumer connects to PostgreSQL using a dedicated service account with the minimum required permissions: `SELECT` and `UPDATE` on `documents`, `UPDATE` on `batches`. It must not use the Supabase service role key, which has unrestricted access.

### Redis credentials (SEC-013)

Redis must require AUTH. The Consumer connects with the Redis AUTH password from environment variables. The Redis instance must not be accessible outside the private network shared by the API, Consumer, and workers.

### No file access

The Consumer must never construct a storage URL from a notification message or database record and fetch it. Object keys are passed to workers inside the Celery task payload — the Consumer does not use them for any I/O.

### PII in logs (SEC-015)

Log only `document_id`, `batch_id`, `doc_type`, and `queue_name`. Never log `storage_path` (may contain user identifiers), filenames (may contain CNPJ values), or any extracted document content.

### Secrets

| Variable | Source |
|---|---|
| `DATABASE_URL` | Railway Service Variable / AWS Secrets Manager |
| `REDIS_URL` | Railway Service Variable / AWS Secrets Manager |
| `CELERY_BROKER_URL` | Railway Service Variable / AWS Secrets Manager |

## 03.1.7 Performance Requirements

### The Consumer must be fast

Each message must be processed in milliseconds. The work is: one Redis read (message), one database SELECT, one database UPDATE, one Redis PUBLISH (Celery task). Under normal conditions this completes in < 50ms.

If the Consumer becomes a bottleneck (large batches submitted simultaneously), run multiple Consumer instances. Consumer instances are stateless — multiple can run concurrently without coordination because each processes a different message.

### Connection pools

Use persistent connections, not per-message connections. Establish the database connection and Redis connection once on startup and reuse them across all messages.

### Idempotency

If the same notification is delivered twice (Redis at-least-once delivery), the second processing attempt must be safe. Before publishing a task, check the document's current status:
- If `upload_confirmed`: process normally
- If `queued` or later: discard the notification — the task was already published

## 03.1.8 Testing Requirements

### Must pass before any deployment

**T-CRIT-007 — Consumer discards messages for unknown document IDs**
Submit a notification with a `document_id` that does not exist in the database. The Consumer must log a warning and discard the message — not raise an unhandled exception, not publish a task.

**T-CRIT-008 — Consumer does not publish a task if status is not upload_confirmed**
Submit a notification for a document already in `queued` status. Assert no new Celery task is published and the status is not modified.

### High priority

**T-HIGH-008 — Status transition is atomic with task publication**
Simulate a Redis publish failure after the database has been updated. Assert the document is rolled back to `upload_confirmed`, not left in `queued` with no corresponding task.

**T-HIGH-009 — Concurrent notifications for the same batch**
Submit 50 upload confirmation notifications simultaneously for documents in the same batch. Assert `batch.queued_count` equals 50 after all are processed — no race condition in the atomic increment.

**T-HIGH-010 — Correct queue routing per doc_type**
For each of `xml`, `pdf`, `img`: submit a notification, assert the task lands in the correct Celery queue (`queue.xml`, `queue.pdf`, `queue.img`).

### Integration tests

Use a real Redis instance and `testcontainers-python` for PostgreSQL. Do not mock either. The Consumer's correctness depends on actual Redis pub/sub behavior and real PostgreSQL transaction semantics.

## 03.1.9 Implementation Notes

### Package location

The Consumer runs as a long-lived process inside `invoice-pipeline`. It is not a Celery worker — it does not use `@app.task`. It is a standalone Python process that uses the `redis-py` pub/sub interface and publishes to Celery queues using `celery_app.send_task()`.

### Redis client (FW-014)

Use `redis-py ≥ 5` (sync interface, since the Consumer is a blocking loop). The same `redis-py` package is used by both the Consumer (sync) and the API (async via `redis.asyncio`).

### Celery task publishing

Use `celery_app.send_task(name, kwargs=payload.model_dump(), queue=queue_name)`. Never construct the raw Redis message manually. The `celery_app` instance in `invoice-pipeline` is the single source of truth for queue names and serialization configuration.

### Structured logging

Use `structlog` with JSON output. Bind `document_id` and `batch_id` at the start of each message processing cycle using `structlog.contextvars.bind_contextvars()`. All subsequent log lines within that cycle automatically include these fields.

### Dependency management (FW-009)

`invoice-pipeline` is a `uv` workspace member. The Consumer shares the same virtual environment as the Celery task definitions — no separate install needed.

## 03.1.10 What Not To Do

**Do not download files.**
The Consumer receives a `document_id`. It fetches `doc_type` and `storage_path` from the database for the purpose of constructing the task payload only. It does not use `storage_path` to fetch anything.

**Do not classify by filename or extension.**
`nota_fiscal.xml.pdf` is a real filename in the wild. Routing by extension is unreliable. The `doc_type` in the database is set by the API from the validated, normalized MIME type declared at upload time.

**Do not publish a task before confirming the upload.**
The API publishes the notification only after upload confirmation. The Consumer should not be modified to accept notifications from any other source or at any earlier point in the upload lifecycle.

**Do not update document status to `failed` or `completed`.**
Status writes beyond `queued` belong exclusively to workers and the DLQ worker. The Consumer only moves documents from `upload_confirmed` to `queued`.

**Do not swallow exceptions silently.**
If the database is unreachable or the Celery publish fails, the Consumer must log the error with full context and allow the message to be redelivered — not silently discard it and move on.

**Do not run as root in the container.**
Use a non-root user (uid=1001). The Consumer does not need any elevated permissions.

**Do not use `pickle` for Celery task serialization.**
The Consumer publishes tasks using `celery_app.send_task()` which inherits the app's serializer configuration. The Celery app in `invoice-pipeline` must have `task_serializer="json"` and `accept_content=["json"]` set globally. If these are not set, Celery defaults to pickle — a remote code execution vector.
